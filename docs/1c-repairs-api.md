# Заказ-наряды: подключение расширения 1С

Агрегатор принимает полную карточку ремонта и показывает карточки «В работе»
двумя отдельными списками: «Заказ-наряды» и «Заказ-наряды (тест)». Автомобиль —
переданное из 1С наименование (для юридического лица — наименование договора).
Новые карточки идут первыми по дате
документа; при одинаковой дате порядок определяется UUID. Номер и автомобиль
не являются уникальными: разные документы с одинаковыми реквизитами сохраняются
отдельно. Состав запчастей и вход сотрудников по коду в этот контракт не входят.

В каждой вкладке три колонки: «Наименование», «Готовность товаров» и «Оплата».
При долге и отсутствии оплаты показано «Требуется оплата»; при частичной оплате
или авансе с остатком долга — «Частично оплачен». Оба статуса выделены красным,
под ними показано «Осталось оплатить: 10 500,00» с суммой из 1С. Без долга —
«Оплачено». Пока 1С не передала расчёт, показано «Оплата ещё не проверена».
Под машиной юридического лица отображается организация. Готовность содержит
«В наличии X из Y позиций» и состояние «Все товары в наличии» или «Есть товары
к получению»; для нулевого количества — «Не найдено товаров», без переданного
расчёта — «Наличие ещё не проверено».

## Серверные настройки

Используется существующая `GARAGE_DB_PATH`: отдельная таблица `repair_cards`
создаётся автоматически, без изменения строк или схемы гаража, корзины и
уведомлений. Данные сохраняются после перезапуска и доступны с разных компьютеров.
Сохраняйте эту базу между обновлениями. Резервные копии делайте SQLite backup API
или при остановленном сервисе; при работающем сервисе учитывайте WAL/SHM.

На сервере агрегатора задайте отдельную переменную окружения
`ONEC_REPAIRS_INTEGRATION_SECRET`. Допустимы 32–256 символов ASCII: латинские
буквы, цифры, `_`, `-`. Рекомендуется сгенерировать 32 случайных байта, например
`node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`,
и поместить результат в менеджер секретов или защищённое окружение службы.
Не помещайте значение в исходники, `.env.example`, журналы, URL или браузер.
Приложение не загружает `.env` автоматически. После изменения секрета перезапустите
службу. Пустое/отсутствующее значение отключает только приём из 1С (`503`);
чтение списка и остальные функции продолжают работать. Некорректное непустое
значение останавливает запуск с ошибкой конфигурации без вывода самого секрета.

Для Bearer-аутентификации отправитель также должен знать секрет. Храните его
в защищённых серверных настройках 1С и выполняйте HTTP-запрос на сервере 1С;
не передавайте его клиентской форме и не зашивайте в код расширения. Это отдельный
секрет, независимый от учётных данных поставщиков и master key шифрования.
Агрегатор получает его только из окружения, не сохраняет в SQLite, не возвращает
в API и не загружает во frontend.

Сервер по-прежнему слушает loopback. Для удалённого сервера 1С используйте HTTPS
через доверенный reverse proxy с проверкой сертификата. Для маршрута приёма
настройте передачу `Authorization` и доступ сервера 1С без интерактивного входа
в веб-интерфейс. Не открывайте таким исключением остальные `/api/*`: интерактивный
доступ к ним защищается встроенной авторизацией агрегатора и, при необходимости,
дополнительным reverse proxy. Для `/api/repairs` обычный пользователь получает
только карточки с совпадающим `responsibleFio`; администратор получает полный список.
Дополнительный CORS не включается. Исключите заголовок Authorization и тела
запросов из журналов reverse proxy/1С.

## Приём одной карточки

`POST /api/integration/1c/repairs`

Заголовки:

```http
Authorization: Bearer <секрет из серверных настроек>
Content-Type: application/json; charset=utf-8
```

Тело — ровно один JSON-объект в UTF-8 без BOM. Массивы, `null`, неизвестные
поля, неполные карточки и параметры URL отклоняются. Лимит тела — 16 KiB
(16 384 байта). Пять основных полей обязательны; дополнительно
разрешены `responsibleFio`, `testPlatform`, `counterpartyName`, `goodsReadiness`, `paymentStatus` и `amountDue` (см. ниже):

| Поле | Формат и ограничение | Источник в 1С |
| --- | --- | --- |
| `documentId` | UUID с дефисами, 36 символов, не нулевой; регистр не важен, хранится в нижнем | Строка UUID ссылки документа, не его номер |
| `number` | До 64 символов | Номер документа, включая префиксы и ведущие нули |
| `date` | Реальная дата `YYYY-MM-DDTHH:mm:ss`, ровно 19 символов | Дата и время документа в часовом поясе базы 1С |
| `vehicleName` | До 500 символов; пустая строка допустима только с непустым `counterpartyName` | Наименование контрагента; для юридического лица — наименование договора |
| `status` | До 200 символов | Текущее текстовое представление состояния ремонта |
| `responsibleFio` | До 256 символов | ФИО значения «Ответственный» из заказ-наряда |

Необязательное `counterpartyName` — непустое наименование юридического лица
до 500 символов с теми же правилами пробелов и управляющих символов.
Необязательное `goodsReadiness` — объект ровно с двумя целыми числами:
`totalPositions` от 0 до 100000 и `availablePositions` от 0 до `totalPositions`.
Это фактически рассчитанная в 1С готовность товарных позиций. `null`, дроби,
отрицательные числа и неизвестные поля отклоняются. Агрегатор сохраняет эти
поля и возвращает их в подтверждении и списке, не вычисляя значения сам.
Необязательное `paymentStatus` принимает `paid`, `payment_required` или `partially_paid`.
Расширение рассчитывает его так же, как поле «Должен» в заказ-наряде:
итог работ и запасов (`Всего`) минус `СуммаОплаты + СуммаАванса` из
`РегистрСведений.ФактОплатыЗаказов` по `СчетНаОплату`, округлённый до копеек.
Положительный остаток при положительной сумме оплаты/аванса — `partially_paid`,
без неё — `payment_required`. Нулевой остаток или переплата — `paid`.
Оплата, аванс и возврат меняют статус при очередной сверке, даже без повторного
сохранения заказ-наряда; ручное обновление получает тот же расчёт.
Расширение всегда передаёт `amountDue` — число в валюте документа с максимум
двумя десятичными знаками, от 0 до 9 999 999 999 999,99. При `paid` оно равно 0,
при долговых статусах строго положительно; для `partially_paid` обязательно.
Сумма без статуса, `null`, отрицательные числа, дроби меньше копейки и
противоречащие статусу суммы отклоняются. SQLite хранит сумму целым числом копеек.
Старые `paid`/`payment_required` без суммы совместимы с прежним отправителем;
без полученной суммы долга интерфейс явно сообщает «Сумма долга ещё не получена
из 1С». Ноль вместо неизвестной суммы не подставляется; обновите карточки из 1С.
Миграция расширяет прежний CHECK статусов в обеих таблицах, сохраняя все строки,
готовность и старые статусы. Новый столбец суммы у старых карточек остаётся NULL.
Существующие карточки обеих платформ сохраняются при обновлении базы и получают
статус после следующей передачи из 1С. Отсутствие поля означает неизвестную оплату.
Необязательное `responsibleFio` — ФИО ответственного сотрудника. Обычный
пользователь видит только карточки с совпадающим ФИО, администратор — все карточки.
Карточка без этого поля доступна только администратору, поэтому расширение 1С
должно передавать его для рабочих заказ-нарядов.
Повторная полная карточка без необязательного поля удаляет прежнее значение.

Начальные и конечные пробелы строк удаляются; управляющие символы запрещены.
Ограничения длины проверяются до удаления пробелов, в кодовых единицах UTF-16.
Дата не содержит `Z` или смещение часового пояса. Она хранится без преобразования
и показывается как в 1С (`ДД.ММ.ГГГГ ЧЧ:мм`); секунды сохраняются в API/SQLite.
Пустые поля не заменяются вымышленными значениями. У юридического лица без
наименования договора передаётся пустой `vehicleName` и непустой `counterpartyName`;
интерфейс показывает «Договор не указан». Статус передаётся дословно, но список
возвращает только точное значение «В работе»; прочие карточки сохраняются в базе.

Структура JSON ниже — шаблон контракта, значения в угловых скобках нужно заменить
реальными данными. Шаблон сам по себе не является валидной карточкой:

```json
{
  "documentId": "<UUID ссылки документа 1С>",
  "number": "<номер документа>",
  "date": "<YYYY-MM-DDTHH:mm:ss>",
  "vehicleName": "<наименование контрагента>",
  "status": "<состояние ремонта>",
  "responsibleFio": "<ФИО ответственного>"
}
```

Успешный ответ для создания и обновления: `200 OK`, `Cache-Control: no-store`.

```json
{
  "repair": {
    "documentId": "<UUID документа в нижнем регистре>",
    "number": "<номер документа>",
    "date": "<YYYY-MM-DDTHH:mm:ss>",
    "vehicleName": "<наименование контрагента>",
    "status": "<состояние ремонта>"
  }
}
```

UUID является первичным ключом SQLite. Повторная отправка выполняет атомарный
`INSERT ... ON CONFLICT ... DO UPDATE`: заменяет все реквизиты карточки,
сохраняя одну запись. Последний успешно принятый запрос определяет данные;
версионность и сравнение времени изменения документа пока отсутствуют. Поэтому
передавайте обновления одного UUID последовательно и не повторяйте устаревшую
карточку после новой. Контракт рассчитан на одну базу 1С.

При сетевом обрыве/таймауте результат может быть неизвестен отправителю: безопасно
повторить ту же полную карточку с тем же UUID. Для временных `500`/`503` применяйте
ограниченные повторы с паузой, сохраняя порядок по UUID; при `503` сначала проверьте
настройку интеграции. Ошибки `400`/`401`/`413`/`415` требуют исправления данных или
настроек. Отправляйте карточки после успешной записи документа; внешнюю сеть
не следует включать внутрь транзакции его записи.

## Чтение списка

`GET /api/repairs` — без тела и параметров URL. Используется интерфейсом агрегатора,
не требует секрета интеграции, но требует интерактивной сессии с правом
«Заказ-наряды»; администратор видит все карточки.
Ответ: `200 OK`, `Cache-Control: no-store`.

```json
{ "repairs": [] }
```

При наличии данных `repairs` содержит полные объекты с основными и переданными
необязательными полями.
Список содержит все карточки со статусом «В работе», без пагинации или скрытого
ограничения количества. Прочие статусы не возвращаются.
Интерфейс загружает список при открытии, по кнопке «Обновить» и каждые 10 секунд
в видимой активной вкладке. При ошибке фонового запроса ранее полученные данные
остаются на экране, отображается сообщение о неудачном обновлении.

## Ошибки

Любая прикладная ошибка возвращает JSON вида `{ "message": "Описание ошибки" }`,
без stack trace, содержимого запроса, секретов и внутренних путей.

| HTTP | Значение |
| --- | --- |
| `400` | Некорректный JSON/карточка, невозможная дата или параметры URL |
| `401` | Секрет отсутствует или неверен; заголовок `WWW-Authenticate: Bearer` |
| `405` | Недопустимый HTTP-метод; допустимый указан в `Allow` |
| `413` | Тело превышает 16 KiB |
| `415` | Content-Type отличается от application/json |
| `500` | Ошибка чтения/записи SQLite; данные не подменяются пустым успехом |
| `503` | На сервере не задан секрет интеграции |

Неверный секрет проверяется до разбора тела, сравнение выполняется через
`timingSafeEqual` по SHA-256 дайджестам одинаковой длины. Шлюз может отдельно
возвращать собственные ошибки TLS, сетевого доступа и аутентификации.

## Проверка подключения на реальных данных

1. Настройте серверный секрет и HTTPS-маршрут, сохраните прежнюю `GARAGE_DB_PATH`.
2. Выберите существующий записанный заказ-наряд «В работе» и передайте фактические поля.
3. Откройте «Заказ-наряды»: проверьте машину, организацию второй строкой для юрлица,
   состояние готовности и «В наличии X из Y позиций».
4. Измените готовность в 1С и передайте карточку с тем же UUID: строка обновится
   автоматически. Другой статус скроет карточку; возврат «В работе» вернёт её в список.
5. Перезапустите агрегатор и снова откройте список: карточка должна сохраниться.

Эта реализация добавляет принимающую сторону агрегатора. Отправка из расширения подключается серверным модулем, постоянной очередью
и формой настроек. См. дополнение о тестовой платформе ниже.


## Тестовая платформа (расширение 1С)

В тело карточки можно добавить необязательное логическое поле `testPlatform`.
При `true` карточка хранится в отдельной таблице `test_repair_cards` и показывается
только во вкладке «Заказ-наряды (тест)». При отсутствии поля или `false` сохраняется рабочий
контракт. У одной пары UUID/платформа одна запись: тестовая копия с тем же UUID
никогда не обновляет рабочую карточку. Рабочая вкладка показывает только рабочие
карточки. API чтения возвращает обе платформы;
у тестовых карточек присутствует `testPlatform: true`.

`GET /api/integration/1c/repairs/status` с заголовком Bearer проверяет адрес и
секрет без создания данных. Успех —
`200 { "ready": true, "cards": { "production": 0, "test": 0 } }`, где числа
отражают фактическое количество карточек каждой платформы в одном снимке SQLite.
Счётчики доступны только с секретом интеграции.

`DELETE /api/integration/1c/repairs/test` с тем же Bearer, Content-Type application/json
и телом `{ "confirmTestCleanup": true }` удаляет только `test_repair_cards`.
Успех — `200 { "deleted": количество }`.
Для рабочих карточек используется отдельный `DELETE /api/integration/1c/repairs/production`
с теми же заголовками и телом `{ "confirmProductionCleanup": true }`.
Подтверждение другого режима не принимается. Повторная очистка пустого режима
возвращает `deleted: 0`. Другая платформа, гараж, корзина и документы 1С сохраняются.
До очистки отключите обмен выбранного режима, сохраните настройки и подтвердите
удаление в форме 1С. Команда захватывает блокировку отправителя и очищает очередь,
сверку и отметки первой выгрузки только выбранного режима. При активной отправке
нужно дождаться её завершения. Секрет не передается браузеру агрегатора.

Для удаления одной вышедшей из отбора карточки отправитель использует
`DELETE /api/integration/1c/repairs` с Bearer, JSON и ровно двумя полями:
`{ "documentId": "<UUID>", "testPlatform": false }`.
`testPlatform`, если передан, должен быть логическим; отсутствие означает рабочую
платформу, как в прежнем контракте удаления. Ответ:
`200 { "documentId": "<UUID в нижнем регистре>", "testPlatform": false, "deleted": 1 }`.
Если карточки уже нет, `deleted: 0` также означает успех. Такой же UUID другой
платформы не затрагивается. Проверка секрета, размера тела, Content-Type и JSON
совпадает с приёмом карточки; для общего маршрута `Allow: POST, DELETE`.

### Первая выгрузка и повторная проверка в 1С

При сохранении настроек включённого обмена форма проверяет счётчик только
сохранённого режима. Если он пуст, предлагает первичную выгрузку проведённых
заказ-нарядов со статусом «В работе». Наличие карточек другой платформы не мешает.
Если выбранный режим уже заполнен, повторная первичная выгрузка не создаётся.
Начатая незавершённая выгрузка продолжается через постоянную очередь. При открытии
формы можно увидеть её ход, но вопрос о первой загрузке появляется только после
сохранения настроек. Если от первой загрузки отказались, сохраните настройки ещё раз.

Кнопка «Проверить данные» повторяет **отбор первой выгрузки**: вид операции
«Заказ-наряд», документ проведён, не помечен на удаление, статус «В работе».
В очередь выбранного сохранённого режима попадают все подходящие документы,
включая уже подтверждённые; ограничение фонового пакета в 100 карточек не ограничивает
этот список. Принудительный запуск повторяет выгрузку и не отменяет условия отбора.
Отправитель заново читает документ и рассчитывает товары существующим модулем
готовности; новые поля попадают в полную карточку. Удаление ранее переданных карточек,
вышедших из отбора, продолжает существующая фоновая сверка по UUID/платформе.
Уже созданная очередь при обновлении не стирается: она может содержать необходимые
команды удаления. Новая проверка формирует счётчик только по действующему отбору.
Несохранённые изменения настроек требуют сохранения.
В подтверждении рабочей карточки API может не возвращать `testPlatform`:
расширение трактует отсутствующее поле как `false`. Для тестового режима поле
должно присутствовать и быть равно `true`; несовпадение сохраняет карточку в очереди.
Другой режим эта команда не обновляет. Кнопка «Обновить» в браузере запрашивает
из 1С только показанные документы через отдельную очередь, описанную ниже.
Пустые вкладки каждого режима скрываются
независимо; при появлении данных возвращаются. Общий запрос раз в 10 секунд
обновляет обе вкладки, пока страница видима, в том числе из других разделов.
Если открытая вкладка опустела, интерфейс переключается на «Проценку».
Ошибка запроса не считается пустым списком и не скрывает ранее доступную вкладку.

### Подтверждённое обновление показанных заказов

Агрегатор и исходники расширения обновляются вместе. Один раз сохраните настройки
интеграции с включённым обменом заказ-нарядами: это подключает предопределённое
задание `АС_ОбновлениеЗаказНарядовАгрегатора`. В серверной базе оно работает без
открытых клиентов; регламентные задания и исходящий HTTPS должны быть разрешены.
В файловой базе для тестирования нужен открытый клиент. Используется существующий
секрет заказ-нарядов; отдельный ключ и публикация базы не нужны.

Автоматическая передача изменений работает отдельно от ручного запроса.
Сохранение настроек также включает `АС_ОтправкаЗаказНарядовАгрегатора` (10 секунд)
и `АС_СверкаЗаказНарядовАгрегатора` (60 секунд). Первое задание обрабатывает готовую
очередь, второе выполняет восстановительную сверку с ротацией по 100 документов.
Оба используют общую блокировку отправителя. В серверной базе клиентские таймеры
не запускаются; они оставлены только для проверки файловой базы.

Закрытие заказ-наряда регистрируется даже без локального подтверждения предыдущей
отправки, например после получения карточки через ручную кнопку. Отправитель
перечитывает документ после фиксации и отправляет DELETE конкретного UUID и режима.
Сетевая ошибка сохраняет команду для повтора; подтверждённое отсутствие карточки
также считается успешным удалением. Документ 1С сохраняется. Браузер убирает карточку
при следующем чтении списка по таймеру, без нажатия «Обновить».
В диагностике доступны `repairDelivery` и `repairReconciliation` с расписаниями
и последними запусками. После установки расширения настройки нужно сохранить,
чтобы включить новые задания. Работающий планировщик и сеть обязательны.

`POST /api/repairs/refresh?testPlatform=false` принимает `{ "documentIds": ["UUID"] }`
для 1–200 показанных документов. Состав определяется текущим поиском в списке.
Сервер проверяет каждый UUID по сохранённому режиму и ответственному сотруднику;
переданный клиентом UUID не даёт права доступа. Для рабочего режима требуется
`repairs`, для тестового — `testRepairs`. Администратор видит документы режима.
Только запросивший пользователь может читать и отменять свой запрос.

Ответ 202: `{ "refresh": { "id": "UUID", "status": "pending", "expiresAt": "UTC ISO-8601" } }`.
`GET /api/repairs/refresh/{id}?testPlatform=false` возвращает состояние. При успехе
`status=completed`, `repairs` содержит проверенные карточки, `removedDocumentIds` —
документы, больше не входящие в список. Вместе оба массива должны покрывать ровно
все запрошенные UUID. Изменившийся ответственный не раскрывает карточку прежнему
сотруднику. `DELETE` того же пути отменяет ожидающий запрос.

Расширение выполняет `GET /api/integration/1c/repairs/refresh/requests?testPlatform=false&waitSeconds=5`
с существующим Bearer-секретом. Допускается ожидание 0–20 секунд. Ответ содержит
`request=null` или `{ id, leaseId, documentIds, testPlatform, expiresAt }`. Обращения
обработчика подтверждают его доступность на 45 секунд. Проверка обычного `/status`
не выдаёт подтверждение активности обработчика. Без его обращений создание
обновления возвращает 503, даже если сохранённый список доступен.

Для `POST /api/integration/1c/repairs/refresh/results` используется JSON до 512 KiB:

```json
{
  "requestId": "11111111-1111-4111-8111-111111111111",
  "leaseId": "22222222-2222-4222-8222-222222222222",
  "testPlatform": false,
  "status": "success",
  "repairs": [],
  "removedDocumentIds": ["33333333-3333-4333-8333-333333333333"]
}
```

Карточки используют текущий формат `RepairCard`; `goodsReadiness` обязательно.
Расширение читает только указанные документы и пересчитывает их готовность,
не отправляет полные табличные части и не запускает полную выгрузку. Отсутствующий,
закрытый или снятый с проведения документ возвращается в `removedDocumentIds`.
Внутренняя ошибка не считается отсутствием документа: весь пакет получает `status=error`.

Аренда действует 45 секунд, запрос — 60 секунд. Устаревшая аренда, отменённый
или истёкший запрос отклоняются с 409. Неполный набор, лишние/дублирующиеся UUID,
неверные счётчики, другой режим или изменение сохранённой карточки во время
ожидания означают ошибку всего запроса. Сохранение всех карточек и удалений
происходит одной транзакцией SQLite, частичное обновление не применяется.
Одновременно разрешён один запрос пользователя и до 50 во всём агрегаторе.

Во время ручного обновления показывается индикатор ожидания. При сбое значения
скрыты и показано: «Произошёл сбой обновления заказ-нарядов. Достоверность данных
не подтверждена. Обратитесь в магазин». Состояние неподтверждённых UUID сохраняется
в SQLite; `GET /api/repairs` дополнительно возвращает `unverified` с UUID и режимом
только доступных сотруднику документов. Перезагрузка страницы и обычная фоновая
перечитка не делают эти значения проверенными. Ошибку снимает только полный
успешный ответ из 1С для запрошенных UUID. Подтверждение отфильтрованной части
не разрешает показывать остальные неподтверждённые документы при снятии фильтра.
Если запрос не дошёл до сервера, вкладка сохраняет неподтверждённые UUID при
перезагрузке через sessionStorage. Повторная попытка использует ту же кнопку.

Backend и исходники расширения обновляйте совместно. Для готовности сохраняется
исходная схема `goods_total_positions` / `goods_available_positions`. Если успела
работать ошибочная версия с `total_positions` / `available_positions`, её непустые
счётчики переносятся в исходные колонки в транзакции, затем дубли удаляются.
Вчерашние счётчики, для которых новых значений нет, сохраняются. Новая выгрузка
из 1С для чтения сохранённой готовности не требуется. Старые строки, UUID и
посторонние таблицы сохраняются. До запуска сделайте SQLite-совместимую резервную копию `GARAGE_DB_PATH`.
Для встроенной авторизации задайте `AGGREGATOR_ADMIN_PASSWORD` и при необходимости
`AGGREGATOR_ADMIN_FIO`; эти значения должны поступать из защищённого окружения.
Настройка reverse proxy должна пропускать защищённые Bearer-маршруты интеграции,
включая `DELETE`, без передачи Bearer в интерактивный браузер.

Ручная проверка после загрузки расширения в тестовую 1С:

1. Откройте форму настроек — вопрос первой загрузки не должен появиться.
2. Сохраните включённый тестовый режим с пустым тестовым списком — подтвердите
   первую загрузку. Повторное сохранение заполненного режима не предлагает её снова.
3. При заполненном тестовом списке сохраните пустой рабочий режим в серверной базе:
   вопрос и первая загрузка относятся только к рабочему списку.
4. Измените данные старого заказ-наряда и выполните «Проверить данные»:
   карточка с тем же UUID обновляется, другая платформа сохраняет свою копию.
   Проверьте также список больше 100 подходящих заказ-нарядов. Непроведённый,
   помеченный на удаление и завершённый документы не должны увеличивать счётчик
   повторной проверки. Ранее опубликованный документ, вышедший из отбора,
   должен удаляться фоновой сверкой. Для рабочего режима отсутствие testPlatform
   в подтверждении не должно оставлять ошибку в очереди.
5. На отдельном тестовом стенде проверьте очистку каждого режима при выключенном
   обмене, отказ от подтверждения и сохранность другой платформы. Рабочую базу
   для проверки удаления не используйте.

Отправляющая сторона теперь реализована в исходниках расширения «АС_Автосервис».
Установку расширения и проверку в платформе выполняет администратор 1С.
