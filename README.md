# Autoservice Aggregator

Node.js 26 service that searches configured automotive-parts suppliers and streams normalized results to the browser over SSE.

## Local Run

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm start
```

The application listens on `127.0.0.1:3000` by default. `PORT` can override the port.

For persistent runtime credentials and the PartsAPI applicability key, configure
`SUPPLIER_CREDENTIALS_ENCRYPTION_KEY` as a base64-encoded 32-byte key and keep
`STATE_DIR` outside the application checkout in production. The key is stored
encrypted on the server and can be removed from the applicability settings.

## Safe Git Workflow

Changes prepared by AI agents are published only through task branches named
`codex/<short-description>`. Agents must run the required project checks, stage only files
belonging to the current task, create the commit in that branch, and push it with an
upstream:

```sh
git switch -c codex/<short-description>
git push -u origin codex/<short-description>
```

Direct commits or pushes to `main`, force-pushes, and automatic merges are prohibited.
System approval prompts for `.git` writes or network access must be handled with the
narrowest permission for the required Git command; the security policy must not be
disabled or bypassed.

To load a published task branch on another computer:

```sh
git fetch origin
git switch --track origin/codex/<short-description>
```

## Backend Architecture

- `src/backend/server.ts` is the composition root and process lifecycle entrypoint.
- `src/backend/http/` owns routing, request validation, HTTP/SSE responses, and static files.
- `src/backend/application/` owns search orchestration and supplier-session use cases.
- `src/backend/search-service.ts` is the stable facade that wires application services to supplier adapters.
- `src/backend/session/` owns in-process session state, operation generations, and atomic persisted state.
- `src/backend/suppliers/` contains the supplier contract and isolated integrations.

Dependencies flow from HTTP transport through application services to supplier adapters and external integrations. Supplier-specific payloads and browser behavior do not cross into the HTTP or frontend layers.

The frontend uses native browser modules without a bundler. `src/frontend/app.js` owns DOM state and event wiring, while `result-formatting.js`, `search-stream.js`, and `supplier-search-summary.js` isolate result safety, SSE transport, and summary formatting respectively.

## История поиска

При фокусе поля артикула в проценке и применимости открывается отдельная история
последних 30 запросов без отдельной кнопки. Видны 10 записей, остальные доступны
прокруткой; на низком экране список ограничен свободной высотой окна. При добавлении
31-го уникального запроса самый старый удаляется. Прежняя история сокращается до
30 последних записей. Доступны фильтрация при вводе и кнопка очистки. История
сохраняется в этом браузере после запуска поиска; повторный запрос перемещается
наверх. Для применимости сохраняются все введённые артикулы и выбранные бренды.
Выбор записи заполняет форму; для запуска нажмите «Поиск». Стрелки вверх/вниз
и Enter выбирают запись, Escape закрывает список. История поиска отделена от
истории заказов, корзины и сохранённых результатов; при недоступном хранилище
браузера поиск продолжает работать.

## Варианты написания артикулов ВАЗ

Обычная проценка проверяет исходный номер и его парное написание с нулём
в конце индекса модели: например, `2109-6205012-10` и `21090-6205012-10`.
Оба запроса выполняются даже при наличии результатов первого. Поддерживаются
индексы `11xx` и `21xx`, семь цифр номера детали и необязательный двухзначный
суффикс; записи без разделителей также распознаются. Ненулевую пятую цифру
(`21093`, `21214`, `11194`) правило не удаляет, номер детали и суффикс не меняет.

Жёлтое сообщение над таблицей показывает дополнительный полный или сокращённый
вариант. Оно относится к своей поисковой вкладке и сохраняется вместе с результатами.
В таблице и корзине остаются реальные артикулы, цены, остатки и реквизиты предложения
поставщика. Совпавшие предложения двух запросов не дублируются; разные реквизиты
заказа, склады, цены и остатки сохраняются отдельно.
Запросы каждого поставщика идут последовательно в пределах его общего timeout;
ошибка одного написания не скрывается за успешным ответом другого.
Выбранные аналоги и поиск брендов сохраняют прежние запросы.

Событие SSE `search_started` для такого поиска дополнено необязательным
`articleVariants: [{ article, form: "short" | "full" }]`. Кэш вкладки принимает
тот же необязательный массив; прежние вкладки без него продолжают открываться.
Backend и frontend нужно обновлять вместе; новые зависимости и настройки не требуются.

## Поиск изображений товара

Камера рядом с названием товара в проценке и аналогах, а также пункт ПКМ
«Найти изображения» сразу открывают Google Картинки в новой вкладке
с готовым запросом «бренд артикул». Кнопка камеры имеет квадратную рамку
со скруглёнными углами и оранжевое выделение при наведении.
API-ключи, регистрация и настройки не требуются. Вкладка открывается без доступа
к исходному окну и без передачи адреса страницы агрегатора.

В проценке и аналогах ПКМ по шапке таблицы → «Настройки» позволяет задать общие
ширины столбцов: целое число от 24 до 800 px, и выравнивание слева,
по центру или справа. Изменения сразу видны в обеих таблицах; «Отмена» и Escape
возвращают прежний вид без сохранения. Значения сохраняются в браузере
и на сервере после «Применить». При переносе разных прежних настроек значения
проценки имеют приоритет над аналогами. Свободное место панели занимает «Наименование», а если оно скрыто —
самый широкий видимый столбец. При нехватке места «Наименование» сужается
до 200 px (либо меньшей заданной ширины), чтобы доставка, остаток, цена и корзина
оставались видимыми. Остальные столбцы сохраняют точную ширину. Если даже после
сужения места не хватает, доступна горизонтальная прокрутка. Адаптация не меняет
сохранённые значения: при расширении окна таблица снова заполняет панель.
Это правило действует и в гараже. Изменение мышью отключено.
«Применить» сохраняет все поля одновременно; «Отмена» и Escape отменяют правки.
Кнопки корзины и гаража остаются в компактном столбце фиксированной ширины.
В таблице гаража те же настройки доступны через ПКМ по шапке → «Настройки»:
ширина и выравнивание сохраняются отдельно от проценки, предпросмотр работает
до применения, а «Наименование» занимает свободное место панели. Изменение
ширины мышью отключено во всех трёх таблицах.
Актуализация гаража заново запрашивает предложения поставщика и сопоставляет
артикулы независимо от дефисов и пробелов, сохраняя проверку бренда и склада.
Если предложение не подтверждено или поставщик не ответил, сохранённые сроки
помечаются как прежние. Дата или конец диапазона раньше текущего дня по Самаре
помечается «Срок доставки устарел»; новая дата не выдумывается. Групповой срок
для неподтверждённых позиций не считается подтверждённым.
Существующие сохранённые ширины переносятся автоматически. Маршрут
`/api/ui-preferences/table-column-widths` дополнительно принимает и возвращает
`alignments`; запросы только с `widths` сохраняют прежнее выравнивание.

При входе в автомобиль предложения гаража проверяются заново. Недоступные
и неподтверждённые позиции остаются серыми и недоступны для добавления в корзину.
У каждой позиции есть кнопка корзины, а рядом с «Актуализировать предложения» —
добавление всех подтверждённых позиций автомобиля независимо от фильтров и группы.
Количество берётся из гаража; перед добавлением выполняется новая проверка
предложения, остатка и срока. Дробные количества, неподдерживаемые поставщики,
прошедшие сроки, недостаточный или неизвестный остаток пропускаются.
Кнопки общей корзины, истории заказов и уведомлений доступны в шапке гаража;
пустую корзину также можно открыть. Добавление не оформляет заказ у поставщика.

Для подготовки позиций используется `POST /api/garage/vehicles/:id/cart-offers`
с `revision` и необязательным `itemId`. Ответ содержит обновлённый `vehicle`
и краткоживущие `offers: [{ itemId, offerId, quantity }]`, без реквизитов заказа.
`POST /api/cart/items/batch` принимает `revision` и `offers: [{ offerId, quantity }]`:
до 500 позиций и тело до 64 КБ. Обычные запросы сохраняют лимит 16 КБ.
Пакет добавляется целиком после проверки каждого предложения, версии корзины,
суммарного количества дублей и блокировок неопределённых заказов.

Корзина открывается кнопкой справа от поиска. В строках основной таблицы
кнопка гаража расположена под кнопкой добавления в корзину в одной колонке
с полем количества. Добавление в корзину доступно для PartKOM, Armtek,
Forum Auto и Rossko, включая найденные аналоги этих поставщиков.
В таблице аналогов используются те же поле количества, кнопки корзины и гаража,
ограничение по остатку и общая серверная корзина. Повторное добавление объединяет
количество той же позиции; дальнейшее обновление и оформление идут через обычную корзину.
Количество — целое число от 1 до остатка в найденном предложении; неизвестный
остаток запрещает добавление. Повторные добавления одного товара с одного склада
объединяются. Индикатор показывает общее количество единиц товара.
Кнопка корзины появляется при добавлении товара и скрывается после удаления
последней позиции. Она расположена отдельно от поиска и имеет круглую форму.
Вкладка «Все» открывается по умолчанию; вкладки поставщиков показывают только
их товары и скрывают столбец поставщика. В каждой вкладке отображаются даты
поставки и количество всех товаров. Флажками в строках выбирают позиции для заказа;
общая сумма и самая поздняя конечная дата прихода считаются только по выбранным
позициям. Флажок в заголовке выбирает все доступные товары текущей вкладки.
Если хотя бы одна дата не указана, общий срок не определяется; приблизительные
сроки помечаются знаком `~`. Количество товаров находится под таблицей.
Кнопка `%` рядом с заголовком «Цена» в проценке и аналогах открывает
«Клиентскую наценку». Доступны режимы без наценки, фиксированный процент и
ступени по закупочной цене: для каждой ступени задаётся включительная верхняя
граница цены и процент; выше последней границы действует процент «В иных случаях».
Ступени упорядочиваются по цене, повторяющиеся границы и некорректные числа
не принимаются. Изменения вступают в силу после «Применить»; закрытие окна
сохраняет прежние настройки. Правила общие для проценки и аналогов активной
вкладки поиска и сохраняются в браузере вместе с ней; прежние сохранённые
проценты автоматически восстанавливаются как фиксированная наценка.
Можно показывать обе цены или только нацененную. Флажок «Показывать в корзине»
отдельно управляет закупочными ценами в корзине, подтверждении заказа и итогах.
По умолчанию цена и стоимость позиции показаны в две строки: сверху — жирным
шрифтом с текущей наценкой активной вкладки, снизу — закупочная серым шрифтом.
Без наценки отображается одна закупочная цена. Сортировка, фильтры и средние
цены используют выбранные правила. При добавлении в гараж сохраняется процент,
соответствующий закупочной цене предложения на момент добавления.
Наценка применяется только при отображении;
сохранённая корзина и тестовый заказ используют закупочные цены.
Кнопка с иконкой удаления очищает открытую вкладку после подтверждения:
«Все» удаляет всю корзину, вкладка поставщика — только его товары. Очистка
выполняется атомарно и отклоняется, если корзина изменилась после подтверждения.
Корзина сохраняется на сервере в существующей базе `GARAGE_DB_PATH`; новые
настройки запуска не требуются. Предложения для добавления действуют 5 минут:
после перезапуска сервера или истечения срока повторите поиск.

При открытии корзины автоматически обновляются предложения всех её товаров у
поставщиков: цена, остаток, срок и служебный идентификатор товара. До завершения
обновления содержимое корзины недоступно, а по центру окна показывается сообщение об
обновления; после ошибки обычные элементы снова доступны и ошибка показывается
в корзине. Кнопка
«Оформить заказы» на вкладке «Все» или «Оформить заказ» у поставщика доступна
только после выбора хотя бы одной позиции и использует уже обновлённые данные.
Если корзина изменилась или срок актуальности истёк,
перед подтверждением предложения обновляются снова. Старая позиция Forum Auto
без идентификатора обновляется
автоматически, если найдено ровно одно совпадение по артикулу, бренду и складу.
Если предложение не найдено, неоднозначно или остатка недостаточно, заказ не
отправляется. После успешного обновления открывается обязательное подтверждение
уже с актуальными данными. Результат обновления действует до двух минут.
Товары сгруппированы по поставщикам:
для каждого показаны бренд, артикул, наименование, склад, срок доставки,
количество, цена закупки, стоимость позиции и сумма его заказа. Внизу — общий
итог и зелёная кнопка «Заказать». Вкладка поставщика подтверждает только выбранные
его товары. На вкладке «Все» в заказ входят только отмеченные позиции; остальные
остаются в корзине. «Вернуться в корзину» и Escape отменяют подтверждение без оформления.
Изменение корзины после открытия окна отклоняет действие; нужно заново проверить
актуальный состав. Повторное нажатие во время завершения заблокировано.

После «Заказать» приложение отправляет реальные заказы в Armtek, PartKOM,
Forum Auto и Rossko. Для PartKOM используется только регулярная доставка:
список пунктов самовывоза не запрашивается. Оплата PartKOM, Armtek и Forum Auto
определяется условиями договора с поставщиком; в используемых сценариях их API
не передаётся отдельный способ оплаты. Блок параметров PartKOM в подтверждении
не показывается. Для Rossko параметры также не показываются: сервер выбирает
заданного покупателя, оплату «Через банк», единственный подходящий адрес доставки
и отправляет заказ целиком. Контактное лицо и телефон задаются на сервере через
`ROSSKO_ORDER_BUYER_NAME`, `ROSSKO_ORDER_CONTACT_NAME` и
`ROSSKO_ORDER_CONTACT_PHONE`. Если Rossko предлагает несколько адресов,
нужно задать `ROSSKO_ORDER_DELIVERY_ADDRESS_ID` из данных Rossko. При отсутствии
настроек или однозначного варианта заказ Rossko не отправляется.
Подтверждённое поставщиком количество удаляется из корзины, а форма показывает
номера заказов. Полностью оформленный заказ у любого поставщика выделяется
зелёной рамкой окна; сообщение об успехе и удалении товаров из корзины не показывается.
При частичном оформлении, отказе или неподтверждённом результате пояснения сохраняются.
Даты в результате оформления и истории всех поставщиков показаны как
`дд.мм.гггг чч:мм`, например `25.11.2026 02:41`, без изменения времени поставщика.
Если передана только дата, время не добавляется. В истории Rossko дата показана
в колонке доставки без дополнительной подписи «Желаемая дата».
Для PartKOM после успешного заказа форма также показывает данные
из ответа `basket/motion/{reference}`: дату, деталь, количество, цену, сроки,
состояние, доступные счётчики движения и комментарий. Пустые поля не подменяются
фиктивными значениями. Для Forum Auto форма показывает данные ответа
`addGoodsToOrder`: номер и статус заказа, даты создания и доставки, товар,
заказанное, забронированное и подтверждённое количество, цену и сумму, если
поставщик их вернул.
Для Rossko форма показывает номер, количество, цену и срок из ответа `GetCheckout`,
затем запрашивает `GetOrders` только по созданным номерам для статуса, даты,
доставки, оплаты и суммы заказа. Для Armtek показываются номер, количество, цена
и срок из `createOrder`; дополнительные сведения о статусе, дате и доставке
читаются через `getOrder` по номеру. Если дополнительное чтение недоступно,
подтверждение заказа сохраняется и форма показывает уже полученные данные.
Позиции Armtek и Rossko с одним номером показаны в одной карточке заказа:
номер, дата создания и общая сумма выводятся один раз, сведения о каждом
товаре остаются отдельными. Разные номера заказов не объединяются.

Кнопка истории рядом с корзиной открывает заказы PartKOM, Armtek, Forum Auto
и Rossko. PartKOM показывает единый список без переключателя «Текущие / Архив»;
обычный запрос `basket/motion` не передаёт фильтр `archive`. Armtek показывает заказы
за выбранный период: по умолчанию последние 30 дней, максимум 93 дня за запрос.
Forum Auto возвращает только активные заказы; общий список выданных и
аннулированных заказов его API не предоставляет. Документированный ответ
`listorders(did=0)` с кодом 26 («Активные заказы не найдены») считается пустой
историей, а не ошибкой проверки. Остальные ошибки API не подменяются пустым списком.
Номер заказа Forum Auto всегда
равен постоянному ID `did`; появляющийся или меняющийся `nr` показывается отдельно
как номер документа. Поиск истории учитывает оба значения. Rossko запрашивает последние
500 заказов всех статусов; дата доставки в карточке обозначена как желаемая.
Новые маршруты чтения: `GET /api/order-history/armtek?from=YYYY-MM-DD&to=YYYY-MM-DD`,
`GET /api/order-history/forum-auto` и `GET /api/order-history/rossko`.
Во всех вкладках показаны реальные данные поставщика. При превышении 500
позиций выборка ограничивается; общая сумма неполной выборки
не показывается. Отсутствующие поля остаются пустыми. Цены Armtek показываются
только с подтверждённой рублёвой валютой; ответ с другой валютой отклоняется.
Просмотр истории не отправляет заказы. Новые настройки запуска не нужны.
При открытии истории параллельно проверяются отмены PartKOM, Armtek, Forum Auto
и Rossko. Пока есть непросмотренные отмены, статус «Отменено» выделен красным,
а круглая кнопка истории выделена
красной обводкой с плавно пульсирующим свечением, без изменения размера кнопки.
Панель поиска оставляет место для всего свечения, чтобы оно не обрезалось
границами рабочей области на компьютере и телефоне.
При системной настройке уменьшения движения обводка остаётся статичной.
Индикация появляется до открытия истории: отмены также проверяются
при загрузке страницы и возвращении во вкладку или окно приложения, не чаще раза
в минуту для таких фоновых проверок. Число новых отмен доступно в подсказке кнопки
и её доступном имени. Нажатие статуса «Отменено» применяет обычный фильтр истории
и сохраняет просмотр уже известных отмен всех поставщиков, снимая пульсацию и
красную обводку иконки. Отдельного предложения или экрана просмотра отмен нет.
Открытие и закрытие истории, Escape и другие статусы сами по себе ничего не отмечают.
Ошибка проверки или сохранения просмотра не скрывает известные отмены; повторить
проверку можно кнопкой «Обновить», сохранение — повторным нажатием «Отменено».
Первые обнаруженные отмены также считаются непросмотренными.
Отмены и просмотр хранятся на сервере в таблице `purchase_order_cancellation`
существующей базы `GARAGE_DB_PATH`, автоматически создаваемой при запуске.
Состояние общее для всех компьютеров и пользователей этого экземпляра агрегатора,
как и серверная корзина; настройки авторизации не меняются. Новые маршруты:
`GET /api/order-cancellations` и `POST /api/order-cancellations/seen` с
`{ notices: [{ id, revision }] }`. Ответ содержит `notices` и общее число `total`.
API возвращает до 100 заказов на странице; выбор «Отменено» последовательно
подтверждает известные отмены пакетами до 100 в пределах общего срока 15 секунд.
Новые поступления и более свежие версии уже подтверждённого заказа остаются новыми.
Рост отменённого количества или новая отменённая позиция повторно отмечает заказ
новым. Подтверждение старой версии не скрывает более свежую отмену. Перестановка
строк, изменение описания, цены или склада не создаёт повторное уведомление.
Для поставщиков без идентификатора позиции сравнивается суммарная отмена одинакового
артикула и бренда внутри заказа. Уменьшение количества и сокращение ответа поставщика
не стирают сохранённые отмены. Возврат товара не считается отменой.
Отменённая часть незавершённой позиции Armtek/PartKOM передаётся в необязательном
`items[].cancelledQuantity`; уведомление не выводится из произвольного текста статуса.
Проверка также работает при открытии истории и по «Обновить», без периодического опроса.
Она использует доступную выборку API: Armtek — последние 30 дней, PartKOM и Rossko —
до 500 записей, Forum Auto — только доступные его API заказы. Отмены, которые никогда
не попали в ответ API, обнаружить нельзя. Ошибка поставщика не очищает журнал:
форма сообщает, кого не удалось проверить, а остальные результаты остаются доступны.
Проверки: `node --test tests/browser/cart.test.mjs` и `pnpm test`.
Под вкладками поставщиков доступны группы статусов: «В работе» (в обработке,
в пути, на складе), частичная поставка, отменено, получено и возвращено.
«Все заказы» снимает выбор статуса; здесь также видны позиции с неуточнённым статусом.
Вкладка «Придут сегодня» отбирает заказы, в которых хотя бы одна ещё не полученная,
не отменённая и не возвращённая позиция имеет ожидаемую дату доставки на сегодня
по местному времени пользователя. Учитывается ожидаемая дата позиции, а не дата
создания заказа или гарантированный срок; подходящий заказ показывается целиком.
После Rossko расположена выделенная вкладка «Все поставщики»: заказы четырёх
поставщиков загружаются параллельно и объединяются с общей сортировкой. Карточка
сохраняет название поставщика и собственный признак ограниченной выборки.
Ответы показываются по мере загрузки; ошибка одного поставщика не скрывает другие.
Под датами расположена строка поиска по номеру заказа, артикулу, бренду и названию
товара. Поиск применяется сразу без учёта регистра; слова через пробел должны
встречаться в данных одного заказа. Он работает вместе с датами и статусом,
не отправляет запросы поставщикам и показывает подходящий заказ целиком.
Группа статуса и даты «с / по» применяются автоматически. Смена группы не отправляет
новые запросы. Изменение дат заново запрашивает только Armtek, которому нужен
серверный период; остальные ответы фильтруются локально. «Обновить» перечитывает
историю открытой вкладки. Даты включают обе границы; при заданном периоде заказы
без даты не показываются. Статус ищется по любой позиции; подходящий заказ
показывается целиком, с сохранением общей сортировки. Фильтры каждой вкладки
сохраняются до перезагрузки страницы.
«Сбросить» появляется при изменении фильтров и возвращает все статусы и пустые
даты и очищает поиск; для Armtek — исходные последние 30 дней. В общей вкладке без дат Armtek
также запрашивается за последние 30 дней; при заданной конечной дате без начальной
используются 30 дней до неё, при заданной начальной без конечной — до сегодня.
Период Armtek свыше 93 дней показывает ошибку только этого поставщика.
Фильтры работают в пределах полученной выборки, без расширения глубины истории API.
Пояснения о глубине истории и ограничении выборки в интерфейсе не показываются.
Ручная integration-проверка: с подключёнными аккаунтами открыть каждую вкладку,
сверить номера, состав, даты, статусы и цены с кабинетом поставщика, для Armtek
повторить выбор другого периода, для PartKOM сверить выданные позиции. Без реальных
credentials доступность методов для конкретных аккаунтов не подтверждается.
Карточки заказов и их позиции показывают цветные метки с подписью: получен,
отменён, в пути, на складе, в обработке, частичная поставка или возвращён.
Для разных состояний внутри заказа показаны отдельные метки и число
позиций; неполная выборка отмечена отдельно. Неизвестный статус остаётся неизвестным,
прошедшая ожидаемая дата не доказывает получение.
Для PartKOM счётчики `releaseCount`, `refusalCount` и `storeCount` имеют приоритет
перед описанием `stateTxt`: выданная позиция не остаётся «переданной в доставку».
Частичная выдача или отмена отображается с подтверждённым количеством.
Если у PartKOM выданное и отменённое количество вместе составляют всё заказанное,
позиция завершена: `items[].fulfillment=partially_cancelled`. В шапке заказа и
таблице показываются отдельные статусы отменённых и полученных товаров.
В таблице показаны две строки той же запчасти: отменённое и полученное
количество, каждая со своим статусом, количеством и суммой. Например, 4 выдано и 6 отменено из 10 не остаётся
«Частичной поставкой». Такая позиция видна в фильтрах «Получено» и «Отменено»,
исключена из «Придут сегодня» и не получает предупреждение о выходном дне.
Подтверждённые количества передаются в необязательном `items[].fulfillmentQuantities`
с полями `delivered` и `cancelled`; frontend не извлекает их из текста статуса.
Разделение строк не удваивает исходное число позиций, количество и сумму в шапке.
Вкладка и значок «Частичная поставка» удалены. Подтверждённые `deliveredQuantity`
и `cancelledQuantity` также разделяются на строки, а оставшееся количество
показывается в обработке. Общая сумма, число исходных позиций и заказанное
количество при разделении не увеличиваются. Статусы `partial` и `partially_cancelled`
сохраняются во внутреннем контракте для учёта количеств и фоновых уведомлений.
Ограниченная выборка больше не скрывает сумму в шапке заказа: рассчитанный итог
помечается «По показанным позициям». Если поставщик не передал все цены, итог — «—».
Armtek «В работе» и Forum Auto «Подтвержден» (`statusId=30`) означают «В пути»;
подтверждённая выдача или отмена сохраняет приоритет.
По правилу владельца проекта PartKOM «Принят в работу», «Заказан у поставщика»,
«Заказ передан поставщику. Поставщик подтвердил наличие товара.» и
«Заказанный артикул в пути на склад ПартКом.» показываются с меткой «В пути».
При пустом `stateTxt` код PartKOM `state=0` также означает «В пути» с пояснением
«Принят в работу»; соответствие кода кабинету подтверждено владельцем проекта.
Счётчики движения сохраняют приоритет, исходные непустые пояснения сохраняются.
Состояние поставщика «На складе» отображается как «В пути» во всех вкладках
истории и в подтверждениях заказа. Пояснения и счётчики сохраняют количество,
а складская подпись также заменяется на «В пути». Позиции `ready` и `in_transit`
объединяются в одну метку заказа. Исходный `ready` в HTTP API и данных поставщика
сохраняется, получение и отмена по-прежнему определяются подтверждёнными данными.
Во всех вкладках поставщиков и «Все поставщики» карточки автоматически сортируются
по дате и времени «Заказано»: сначала новые, затем старые, без даты — последние.
Статусы позиций не влияют на порядок заказов. Сортировка сохраняется при выборе
любой группы статусов, открытии истории, смене поставщика и обновлении списка;
все позиции и их метки внутри подходящего заказа остаются видны.
Шапки карточек и колонки запчасти, доставки, статуса, цены и суммы имеют общие
ширины. Длинные значения переносятся внутри колонки; на узком экране таблицы
прокручиваются по горизонтали внутри карточки.
Для Rossko код `2`, обозначенный в API как «отгружено», отображается завершённым:
зелёная метка «Получен» и текст «Передан покупателю». Такое соответствие кабинету
Rossko подтверждено владельцем проекта; оно применяется к каждой позиции,
поэтому заказ с незавершёнными позициями сохраняет разные метки в заголовке.
Код Rossko `7` («Нет в наличии») отображается отменённым. Отдельного статуса
и фильтра «Требует внимания» нет. Просрочка и незавершённые или отклонённые возвраты
не считаются отменой или завершённым возвратом: метка остаётся неуточнённой,
исходное пояснение поставщика сохраняется. Коды `31` и `36` означают завершённый
возврат. Для кода `31` вместо описания «Ожидаем товар на складе» используется
«Успешно возвращено»: соответствие кабинету подтверждено владельцем по трём
возвращённым позициям и их кодам из API, несмотря на старое описание в документации.
В Forum Auto выдача нулевого количества без подтверждения отмены также остаётся
неуточнённой.
Для Armtek отгрузка сама по себе означает «В пути»; закрытый заказ без
подтверждения поставки не помечается полученным.
История Armtek читает документированный отчёт `ws_reports/getOrderPositionsReportByDate2`:
`Issued` («Выдано») имеет приоритет перед текстовым статусом, поэтому полностью
выданная позиция не остаётся «Частичной поставкой». Исходное заказанное количество
берётся из `ZZKWMENG`, при отсутствии — из `KWMENG`. Отклонения `REJECTED`
(при отсутствии — `KWMENG_REJ`) и отказы клиента `REJ_MENGE` учитываются отдельно
от выдачи. Если выданное и отменённое количество вместе закрывают позицию,
она также показывается двумя строками с `fulfillment=partially_cancelled`.
Сумма счётчиков больше заказанного и некорректные счётчики не подтверждают получение.
Поля описаны в [официальной документации Armtek](https://ws.armtek.ru/?alias=reports&page=service#methgetOrderPositionsReportByDate2_post).
Для новых заказов Armtek, оформленных через агрегатор, срок возврата `RETDAYS`
сохраняется из обновлённого предложения при оформлении. Подтверждение заказа
дополняется необязательными `armtekOrders[].returnDays` и `positionId`, история —
`items[].returnDays` и `positionId`. Это условия предложения, а не поле ответа API
заказа и не оставшиеся дни. Срок сохраняется в таблице `purchase_armtek_return_terms`
существующей SQLite-базы корзины; таблица создаётся автоматически. Связь с историей
проверяется по номеру заказа, позиции `POSNR`, артикулу и бренду. В истории для старых
и внешних заказов, а также при отсутствии срока или номера позиции отображается
«Срок возврата не указан»; в подтверждении известный срок показывается и без `POSNR`.
Нулевой срок означает «Возврат недоступен». Начало отсчёта и конечная дата не вычисляются.
Для PartKOM и Forum Auto сама дата на субботу или воскресенье выделяется жёлтым
фоном с закруглённой рамкой в поиске, аналогах, гараже, корзине, подтверждении
и информации о заказе.
Гарантированная дата всегда отображается обычным текстом без выделения.
После оформления и в истории выходной проверяется только по ожидаемой дате:
это не диапазон с гарантированной датой. Например, ожидаемое воскресенье 18.10.2026
выделяется и при гарантированном сроке 21.10.2026. Бывший статус «На складе» («В пути») тоже
считается активным, пока товар не получен.
В предложениях PartKOM в поиске, аналогах (включая исходную деталь), гараже, корзине и подтверждении
надпись «Послезавтра» выделяется также для будних дней. «Завтра» выделяется только
для выходных. У Forum Auto будний день «Послезавтра» отдельно не выделяется.
Относительный срок определяется по календарным дням в часовом поясе
браузера, как и сама надпись; дни к сроку поставщика не прибавляются.
Длинная дата и диапазон целиком остаются внутри жёлтой рамки; при узкой колонке
текст переносится внутри неё, не перекрывая соседние столбцы.
Для остальных дат выделяются выходные и диапазоны «пт–сб» / «пт–вс». Если интервал включает
другой будний день («сб–вт», «вс–ср», «чт–сб»), выделения нет; отдельная пятница
тоже не выделяется. Правило об отсутствии доставки по выходным
задано владельцем проекта; дата поставщика сохраняется без автоматического переноса.
В истории завершённые, отменённые и возвращённые позиции не получают предупреждение.
В основной проценке и аналогах доступны вкладки «Все предложения» и «В ближайшие дни».
Вторая показывает только завтра и послезавтра по календарю браузера. Для PartKOM
включается только доставка завтра в будний день; послезавтра, суббота и воскресенье
исключены. Диапазон PartKOM должен целиком приходиться на завтрашний будний день.
Для диапазона обе границы должны попадать в эти два дня; сегодня, более поздние
и неизвестные сроки исключены. Приблизительные сроки со знаком `~` также исключены
для всех поставщиков, в том числе приблизительные диапазоны. Во «Всех предложениях»
они остаются доступны с прежней пометкой.
Левые фильтры, средние цены и счётчик пересчитываются по выбранной вкладке;
заданные диапазоны цен/дат и остальные условия применяются к её предложениям. Переключение
не запускает новый поиск и не меняет исходные предложения; новая форма аналогов
открывается на «Всех предложениях». При включении «В ближайшие дни» сортировка
автоматически переключается на доставку по возрастанию: сначала завтра, затем
послезавтра. Диапазон относится к дню своего начала. Возврат ко всем предложениям
восстанавливает столбец и направление сортировки, выбранные до включения вкладки,
даже если внутри неё сортировку меняли вручную. Повторное нажатие активной вкладки
не перезаписывает сохранённый выбор; проценка и аналоги запоминают его независимо.

переходит на существующую доступную кнопку без прокрутки.
Ответы всех маршрутов истории теперь содержат `items[].fulfillment`; backend и
frontend обновляются вместе. Существующий HTTP-параметр `archive` PartKOM сохранён
для прямых клиентов API, интерфейс его не использует. Ручная проверка: сверить
полностью выданную, отменённую и частичную позицию PartKOM со счётчиками в кабинете,
затем сравнить метки остальных поставщиков с их текущими статусами.
Если ответ Forum Auto после отправки неполный или соединение прервалось,
приложение сверяет попытку запросом `listOrders` по номеру заказа или внешнему
идентификатору попытки. Запрос создания заказа при этой сверке не повторяется.
Явный документированный отказ Forum Auto оставляет товар в корзине без блокировки
и показывает причину отказа. Если статус остался неопределённым, позиция
блокируется до ручной сверки. После проверки, что заказа нет в кабинете Forum Auto,
её можно разблокировать кнопкой в строке корзины; подтверждение сохраняется в
журнале попыток. Разблокировка сама заказ не отправляет.
Неподтверждённые позиции остаются. Если ответ поставщика или
соединение прервалось после отправки, статус отмечается как неопределённый:
повторное оформление таких позиций блокируется до ручной сверки в кабинете
поставщика, чтобы не создать дубль. Журнал попыток хранится в той же базе,
что и корзина. Цена и остаток соответствуют обновлению перед подтверждением;
поставщик всё ещё может подтвердить меньшее количество. STParts в корзине не поддерживается.

Маршруты `POST /api/cart/refresh`, `POST /api/cart/order-options` и
`POST /api/cart/order` обновляют предложения, получают параметры выбранных
товаров и оформляют только переданные `itemIds`. Существующий
`GET /api/cart/order-options` остаётся доступен для прежних клиентов.
`POST /api/cart/test-order`
по-прежнему возвращает `testOnly: true` и не обращается к заказным API.
Backend и frontend нужно обновлять вместе; для оформления Rossko требуются
указанные выше настройки сервера.
Браузерная проверка корзины: `node --test tests/browser/cart.test.mjs`.
Ручная проверка с реальными подключениями: найти товары всех четырёх поставщиков,
добавить их в корзину, сверить доставку, оплату и суммы, затем оформить по
одному дешёвому заказу у каждого поставщика. Проверить номера заказов в форме
и кабинетах поставщиков, а также удаление подтверждённых позиций из корзины.
Автоматические тесты не обращаются к поставщикам и не подтверждают работу с
боевыми учётными записями.

В разделе «Применимость» можно вводить до 50 OEM-артикулов через запятую,
например `30676484, 30780376, 30780377`. Каждый артикул проверяется отдельно
для каждого выбранного бренда: сначала используется сохранённый результат,
при его отсутствии выполняется запрос PartsAPI. Повторы артикула и бренда
не добавляются повторно. Пробелы внутри артикула не разделяют список.
Бренд автоматически подставляется из базы только для одного артикула;
для нескольких артикулов выберите бренды вручную. В настройках применимости
можно выбрать от 1 до 32 одновременных поисков, по умолчанию — 8.
Настройка действует для ручного поиска и импорта файла, меняется перед запуском;
после перезагрузки страницы возвращается к 8.

Кнопка с иконкой файла слева от настроек открывает импорт TXT. Простой формат:
одна пара `артикул | бренд` в строке, например `12345 | Hyundai`; результаты
добавляются в активную вкладку. Для исходных артикулов со своими OEM-номерами
поддерживается формат блоков:

```text
Артикул: AMD.FF714
OEM-артикул: 6Q0 201 051 C | Volkswagen
OEM-артикул: 6Q0 201 051 C | Audi

Артикул: AMD.WTB25
OEM-артикул: 7701470460 | Renault
```

Несколько разных исходных артикулов создают новую группу «Группа N»: один
исходный артикул — одна вкладка с его OEM-парами. Окно импорта показывает короткий
пример файла; в предпросмотре указан исходный артикул каждой OEM-строки.
Группа создаётся после нажатия «Начать поиск» и проверки наличия API-ключа.
Один исходный артикул добавляется в текущую вкладку и задаёт её название.
Повторные блоки одного исходного артикула объединяются; одинаковая OEM-пара
в разных исходных артикулах сохраняется отдельно. При продолжении остановленной
очереди используются те же вкладки, даже если активная вкладка уже другая.

Поддерживаются UTF-8, UTF-16 с BOM и Windows-1251; лимит — 1 МБ, 5000 непустых
строк и 100 исходных артикулов. Перед запуском показывается предпросмотр.
Пустые строки игнорируются, неверный формат, неизвестные бренды и повторы
отмечаются и пропускаются.
Бренды сверяются со справочником с учётом регистра, пробелов, дефисов,
диакритики и явных синонимов: `Volkswagen` → `VW`, `Citroen` → `CITROËN`,
`Mercedes Benz` → `MERCEDES-BENZ`, `Fomoco` → `FORD`, `ГАЗ` → `GAZ`,
`ВАЗ` → `LADA`. Синонимы и русские написания основных марок работают также
при поиске в выпадающем списке брендов. Подразделения вроде `VW (FAW)`
сохраняются отдельно. Неоднозначный `GM` требует конкретной марки автомобиля
и помечается в предпросмотре; он не подменяется на Chevrolet или GMC.
Одинаковый артикул разных брендов обрабатывается отдельно.
Поиск выполняется через тот же API с выбранным числом одновременных OEM-пар,
с сохранёнными результатами: используется только артикул без разделителей,
как при ручном поиске. Пустой ответ не запускает поиск исходного написания.
Строки появляются в таблице по мере обработки в порядке файла; готовые результаты
сохраняются при остановке. Закрытие окна позволяет продолжать работу с таблицей,
импорт остаётся в назначенных вкладках; закрытие любой из них останавливает очередь.
После закрытия вкладки продолжение требует повторного выбора файла.
Ошибки отдельных запросов показываются в окне; отказ API-ключа останавливает
очередь. Необработанные строки и строки с ошибкой можно повторить кнопкой
«Начать поиск»; готовые строки повторно не запрашиваются. Сам файл на сервер
не загружается.

Браузерная проверка импорта: `node --test tests/browser/applicability-file-import.test.mjs`.
Нужен Chromium Playwright либо `TEST_BROWSER_EXECUTABLE_PATH`.

Вкладки «Применимости» можно объединять в группы: перетащите одну вкладку
на другую и отпустите после подсказки о создании группы. Появится папка
«Группа 1», «Группа 2» и т. д. Перетаскивание на вкладку или заголовок уже
существующей группы переносит туда только выбранную вкладку. Двойной щелчок
по папке или её контекстное меню позволяет переименовать группу.
В полосе видна только папка с названием группы. При наведении или фокусе
открываются её вкладки; меню остаётся открытым при переходе указателя к вкладкам.
Чтобы вынести вкладку из группы, перетащите её на свободное место полосы
вкладок или в область «Вынести из группы», которая появляется при перетаскивании.
После подсказки и отпускания вкладка становится отдельной и помещается в конец
полосы. Отпускание вне полосы отменяет перенос.
Перетаскивание к краю другой вкладки переставляет её перед или после этой
вкладки; в центре вкладки создаётся или используется группа. Заголовок папки
тоже можно перетащить перед или после другой папки либо отдельной вкладки,
а также в конец полосы. При этом все вкладки группы перемещаются вместе.
При перестановке оранжевая линия на краю показывает место вставки;
при создании группы или добавлении в неё показывается пунктирная рамка.
В меню папки вкладки переставляются за верхний или нижний край другой вкладки.
В контекстном меню вкладки есть «Убрать из группы», а у папки —
«Разгруппировать»; результаты поиска при этом сохраняются. Пустые группы
удаляются, группа с одной оставшейся вкладкой сохраняется.
Если групп больше не осталось, следующая новая группа снова получает имя
«Группа 1».

Крестик рядом с названием группы и пункт «Закрыть группу» в её контекстном меню
открывают предупреждение. После подтверждения закрываются все вкладки группы;
их результаты удаляются из состояния вкладок, сохранённая база OEM остаётся.
Поиск в закрываемых вкладках останавливается. Если закрыты все вкладки,
создаётся одна пустая. В «Проценке» и «Применимости» контекстное меню вкладки
содержит подменю «Закрыть»: текущую, все кроме выделенной, все правее или левее.
Команды относятся к вкладке, по которой открыто меню; порядок соответствует
полосе вкладок, включая вкладки групп. Кнопки выбора файла оформлены одинаково
в импорте OEM и прокси.

Кнопка «Сформировать мультисписок» видна только для вкладки в группе.
Она сразу открывает список всех завершённых поисков этой группы в порядке
вкладок, без выбора галочками. Если завершённых поисков нет, кнопка недоступна.
Вкладки без названия используют введённый артикул или своё текущее название.
Прежние вкладки при обновлении остаются вне групп. В сохраняемое состояние
`autoservice.applicabilityState` добавлены `groups`, `nextGroupNumber` и
`groupId` для каждой вкладки; группы и названия восстанавливаются после перезагрузки.

Браузерная проверка групп: `node --test tests/browser/applicability-tab-groups.test.mjs`.
На экранах до 720 px поля артикула, бренда и кнопки поиска расположены
в отдельных строках, чтобы поле бренда не перекрывало кнопки.

Слева от кнопок формирования списка показаны «Всего артикулов», «Найдено»
и «Не найдено» для текущей вкладки. Каждая пара «артикул + производитель»
считается отдельно. «Найдено» означает завершённый поиск с применимостью,
«Не найдено» — успешный поиск без применимости; незавершённые поиски входят
только в общее количество. Ошибки и отменённые запросы не создают пустых результатов.
Таблица применимости занимает доступную ширину; горизонтальная прокрутка
нужна только когда её три колонки не помещаются (минимальная ширина 560 px).

Список и мультисписок включают завершённые поиски без найденной применимости:
для них остаётся только заголовок «OEM-артикул: … | бренд» без автомобильных строк.
В структурированном списке пустые OEM-блоки после удаления повторов помещаются
в конец раздела своего исходного артикула; порядок заполненных и пустых блоков
внутри каждой группы сохраняется. Список можно сформировать и при отсутствии
найденных автомобилей. Незавершённые поиски и ошибки в список не включаются;
в формате «Сырые данные» сохраняется исходный порядок и пустой массив `[]`.

Браузерная проверка списка с пустыми OEM-блоками:
`node --test tests/browser/applicability-document.test.mjs`.
Нужен Chromium Playwright либо `TEST_BROWSER_EXECUTABLE_PATH`.

В настройках «Применимости» хранится один API-ключ PartsAPI. Его можно
заменить вводом нового ключа или удалить. Запасные ключи и переключение между
ключами не используются. Все реальные обращения используют этот ключ;
при подтверждённом лимите IP тот же запрос может повториться через прокси.
Учёт обращений и выбор соединения описаны в разделе «PartsAPI proxies».
Приложение не запрещает явную повторную попытку после отказа PartsAPI.

Отказ PartsAPI 401/403/429 отображается красным уведомлением вместо строки под
поиском: «PartsAPI отклонил запрос для ключа …ABCDE. Проверьте ключ и подписку.»
Уведомление содержит только последние пять символов ключа; ключ длиной до пяти
символов скрыт полностью. Исходный ответ поставщика не раскрывается.
Сохранённые результаты остаются доступны и не перекрывают уведомление об отказе.
HTTP-статус 401 и формат ошибки `{ message }` сохраняются.

Состояние `GET/PUT/DELETE /api/applicability/api-key` содержит `configured`,
`persistent` и `maskedKey` (маска либо `null`). Маршруты запасных ключей
`/api/applicability/api-key/fallbacks`, `/api/applicability/api-key/fallbacks/:index`
и ручного выбора `/api/applicability/api-key/active` удалены.

Существующие зашифрованные файлы версий 1/2/3 читаются автоматически: остаётся
текущий выбранный ключ версии 3, а если выбранного ключа нет — исходный или
первый сохранённый ключ. Счётчики и остальные ключи больше не используются.
При сохранении ключа файл записывается в исходном формате версии 1 с одним
ключом; при удалении удаляется файл ключа целиком. Перед обновлением сохраните
защищённую резервную копию файла, если нужны прежние запасные ключи. Backend
и frontend нужно обновлять вместе из одной ревизии.

Отдельная браузерная regression-проверка уведомления:
`node --test tests/browser/applicability-limit-notification.test.mjs`.
Нужен Chromium Playwright либо путь к Chromium-совместимому браузеру в
`TEST_BROWSER_EXECUTABLE_PATH`. Проверка использует только тестовые ответы API.

В «Применимости» справа можно открыть панель сохранённых OEM-артикулов.
Она скрыта при загрузке страницы и оформлена как гараж: ширина 260 px,
изменение в пределах 180–420 px. Панель показывает сохранённые пары
«OEM-артикул + бренд», поддерживает поиск и виды «По брендам» и «По артикулам».
По умолчанию отображаются только записи с найденной применимостью;
пустые результаты можно включить опцией «Показывать не найденные».
Они выделяются приглушённым цветом и пометкой «не найдено». Рядом с брендом
показано число найденных артикулов, а при включённой опции — также не найденных.
Счётчики учитывают весь список по текущему поиску, включая незагруженные страницы.
Нажмите артикул или выберите «Добавить в активную вкладку» в контекстном меню,
чтобы загрузить сохранённую применимость без PartsAPI и API-ключа.
«Удалить из базы» удаляет выбранную пару после подтверждения в панели;
уже открытые результаты во вкладках сохраняются. Следующий явный поиск
может заново сохранить удалённую пару. Список загружается страницами по 100 записей.

Новые HTTP-операции панели: `GET /api/applicability/saved-articles`
(`search`, `offset`, `order=brand|sku`, `includeNotFound=true|false`, по умолчанию `false`),
`GET /api/applicability/saved-articles/result` (`sku`, `brand`) и
`DELETE /api/applicability/saved-articles` (JSON `{ sku, brand }`).
Ответ списка содержит статус `hasResults` для каждой записи и `brandCounts`
с полями `brand`, `found`, `notFound` для счётчиков.

## Инструкция для AI-агентов и будущих правок

Этот раздел является maintenance contract проекта. Перед изменением кода AI-агент обязан прочитать `AGENTS.md`, этот раздел, `package.json`, `tsconfig.json`, связанные production-файлы и тесты. Нельзя исправлять симптом, не установив фактическую причину по коду, документации поставщика и воспроизводимому ответу приложения.

### Основной принцип

- Делайте минимальное корректное изменение. Не переписывайте работающий модуль целиком и не смешивайте исправление с несвязанным рефакторингом.
- Не меняйте HTTP routes, methods, status codes, JSON schemas, SSE event types, `SupplierId`, `NormalizedSearchResult`, сортировку, persisted frontend state и правила выбора поставщиков без явного решения владельца.
- Защитное изменение допустимо, если оно устраняет crash, race condition, утечку, бесконечное ожидание, небезопасный ввод или преобразование реальной ошибки в ложный успех.
- Не добавляйте compatibility branch, fallback или abstraction «на будущее». Сначала должен существовать конкретный контракт или подтвержденное повторение.
- Не угадывайте внешний payload. Сначала получите документацию или безопасный structural diagnostic, затем зафиксируйте наблюдаемую форму regression-тестом.
- Не удаляйте пользовательские файлы, `.state`, credentials, cookies или несвязанные изменения рабочего дерева. Каталог `patrkom test/` не относится к production composition и не должен изменяться без отдельного запроса.

### Направление зависимостей

Соблюдайте направление:

```text
frontend / HTTP transport
  -> application services
  -> supplier adapter contract
  -> concrete supplier integration
  -> external HTTP API / browser / filesystem
```

- `src/backend/server.ts` только собирает приложение, запускает HTTP server и закрывает shared resources.
- `src/backend/http/` отвечает за routing, parsing, validation, security headers, JSON/SSE transport и static serving. Здесь не должно быть supplier business logic.
- `src/backend/application/` оркестрирует поиск, авторизацию, logout и session validation. Application services получают concrete operations через composition root, а не импортируют supplier infrastructure напрямую.
- `src/backend/search-service.ts` является composition facade. Concrete adapters, authorization functions и state cleanup связываются здесь.
- `src/backend/session/` управляет runtime credentials, состояниями сессий, поколениями операций и атомарной записью файлов.
- `src/backend/suppliers/` содержит независимые adapters. Один supplier не должен импортировать или изменять другой.
- Frontend не должен знать исходные payload поставщиков. В браузер передаются только нормализованные результаты и стабильные SSE events.
- Не создавайте циклические imports, универсальные `manager/utils/helper` без одной ясной ответственности или wrapper ради одного простого вызова.

### HTTP и SSE contracts

- URL запроса разбирается только относительно фиксированного `http://127.0.0.1`; `Host` header не является доверенным.
- Request body ограничен, malformed JSON получает предсказуемый `400`, чрезмерный body получает `413`.
- Article и supplier IDs валидируются до вызова application service.
- Static serving обязан оставаться внутри `src/frontend`; path traversal возвращает `404`.
- Security headers должны устанавливаться и для JSON, и для static responses.
- Поиск использует существующий SSE contract: `search_started`, `supplier_status`, `result`, `search_completed`, `fatal_error`. Payload и порядок lifecycle нельзя менять только в backend или только во frontend.
- Ошибка одного supplier не завершает параллельный поиск остальных. `fatal_error` разрешен только для ошибки всего search process.
- Client disconnect должен abort-ить authorization, validation и search. Abort не логируется как unexpected internal error.
- Любой внешний request обязан иметь caller `AbortSignal`, bounded timeout, response-size limit, ограниченные retries и проверенный HTTPS origin.
- Shared HTTP agents и browser resources закрываются при shutdown.

### Ошибки и безопасная диагностика

- Используйте typed errors из `src/backend/errors.ts`: `SupplierAuthError`, `SupplierTimeoutError`, `SupplierIntegrationError`, `SupplierSessionInvalidatedError`.
- Не определяйте timeout по тексту сообщения. Проверяйте тип ошибки или typed abort reason.
- Public HTTP mapping сохраняется: validation `400`, authorization `401`, integration `502`, timeout `504`, internal `500`.
- Raw exception messages, upstream payloads, credentials, URLs с query, filesystem paths, cookies и tokens не должны попадать в HTTP, SSE или logs.
- `SupplierIntegrationError.publicMessage` используется только как явный opt-in для заранее сформулированного безопасного сообщения. Никогда не присваивайте туда upstream `message`, `detail`, HTML или сериализованный payload.
- `SupplierIntegrationError.diagnosticCode` может содержать только безопасный stage/schema code. Допустимы имена полей и типы без значений; запрещены payload values, login, customer ID, URL, article и credentials.
- Поиск показывает `publicMessage` только для typed integration error. Без явного opt-in остается `Supplier search failed`.
- Operational logs должны содержать только operation, category и безопасный diagnostic code. Не добавляйте временные dumps и `console.log`; единственный обычный startup log находится в `server.ts`.
- При диагностике реального supplier сначала воспроизведите публичный lifecycle через `/api/suppliers/sessions` и `/api/search?stream=once...`. Если данных недостаточно, добавьте безопасный stage-code и regression-тест, а не раскрывайте raw response.

### Session lifecycle и persisted state

- Authorization является exclusive operation для конкретного supplier: она отменяет старые операции и блокирует новые до завершения.
- Успешная новая session вызывает `supersedeOthers`, чтобы поздний старый search или state write не пережил смену credentials.
- Logout сначала инвалидирует операции, затем очищает runtime credentials и persisted supplier state.
- Каждый async state write проверяет generation непосредственно перед atomic replace. Stale operation не может восстановить файл после logout.
- Persisted JSON заменяется атомарно; directory/file permissions остаются `0700`/`0600` там, где ОС это поддерживает.
- В production `STATE_DIR` обязателен, является абсолютным и находится вне application checkout.
- Не удаляйте существующие state files во время тестирования: они могут содержать активные sessions.
- Успешно проверенные runtime credentials сохраняются на диск только при настроенном `SUPPLIER_CREDENTIALS_ENCRYPTION_KEY`: AES-256-GCM ciphertext находится в `STATE_DIR`, а master key поступает отдельно из secret manager/environment.
- Без `SUPPLIER_CREDENTIALS_ENCRYPTION_KEY` runtime credentials живут только в памяти процесса. Master key нельзя хранить рядом с ciphertext, в checkout или logs.
- При auth-expiry session validation один раз повторяет полноценную авторизацию с сохраненными credentials. Authorization rejection очищает supplier state и credentials; timeout/integration error не запускает бесконечные retries.
- Не обрезайте password через `trim()`. Login нормализуется отдельно; пробелы password могут быть значимыми.
- Неудачная повторная авторизация должна завершиться typed authorization error и HTTP `401`, даже если старая session остается действующей.
- Каждый adapter обязан иметь отдельный lightweight `validateSession`. Нельзя проверять сессию путем product search с последующим выбрасыванием результатов.

### Нормализация supplier data

Каждый emitted `NormalizedSearchResult` обязан удовлетворять следующим условиям:

- `supplier` совпадает с adapter ID;
- `brand`, `article`, `title` являются непустыми строками из реального ответа;
- article соответствует запрошенному по supplier-specific normalization;
- `price` является конечным положительным числом;
- `warehouse` содержит реальное название/код или `null`;
- `deliveryDate` и `deliveryDateTo` являются валидными ISO dates или `null`, причем конец интервала позже начала;
- `deliveryDateApproximate` отражает качество исходного срока;
- `link` использует только `http:` или `https:` и ожидаемый supplier site;
- отсутствующие значения не заменяются выдуманными складами, датами, ценами, остатками или ссылками.

Если supplier вернул часть валидных и часть невалидных предложений, валидные можно отдать, а невалидные отфильтровать. Если весь непустой ответ оказался невалидным, это integration error, а не успешный пустой результат.

### Правило пустого результата

- Пустой success допустим только для документированного и структурно валидного ответа «предложений нет».
- HTTP error, supplier error flag, error envelope, malformed JSON/HTML, отсутствующая обязательная response collection и полностью невалидные offers не превращаются в `[]`.
- Не восстанавливайте старые `return []`, `return null`, пустые catch или mock fallback ради того, чтобы UI выглядел успешным.
- Один supplier error остается локальным `supplier_status`; поиск других suppliers продолжается.

### Подтвержденные особенности поставщиков

#### Rossko

- Production использует только официальный SOAP API `https://api.rossko.ru/service/v2.1/`.
- Пользователь вводит K1 и K2 в настройках поставщика. Ключи проверяются запросом `GetCheckoutDetails` и при наличии master key сохраняются в общем зашифрованном credential store.
- Для `GetSearch` приложение автоматически выбирает первый адрес и совместимый с ним способ доставки, полученные из `GetCheckoutDetails`; если адресов нет, используется доступный способ «Самовывоз».
- Обычный поиск возвращает только точные совпадения артикула. Аналоги извлекаются из `crosses` отдельным действием пользователя.
- Ответы SOAP ограничиваются по размеру, валидируются как XML и не превращаются в успешный пустой список при ошибке API.
- Документированные ограничения Rossko — не более 80 карточек в `PartsList` и не более 80 кроссов на карточку; приложение не может получить скрытые API позиции обходным способом.

#### Armtek

- Используется только официальный WebService API; не возвращайте ETP/browser fallback.
- Credentials проверяются через `getUserVkorgList` и `getUserInfo`. Найденные `VKORG` и `KUNNR_RG` сохраняются с hash активного login; state другого login применять нельзя.
- `getUserVkorgList`, `search` и `getStoreList` могут возвращать либо прямой массив, либо объект с `ARRAY`. Обе документированные/наблюдаемые формы поддерживаются.
- Основной search отправляет `VKORG`, `KUNNR_RG`, `PIN`, `QUERY_TYPE=1` и только реально настроенные optional parameters.
- Основной поиск Armtek использует только `QUERY_TYPE=1` и не запускает поиск аналогов автоматически. Аналоги запрашиваются по действию пользователя для одной выбранной пары `PIN`/`BRAND` через отдельный поток `/api/search?mode=analogs`; Armtek получает один запрос `QUERY_TYPE=2`, а из ответа выдаются только позиции с признаком `ANALOG`, без дубликатов.
- `DLVDT` и `WRNTDT` образуют интервал поставки; невозможные календарные даты отбрасываются.
- `KEYZAK` по документации является кодом склада, а `getStoreList` преобразует его в человекочитаемое `SKLNAME`. Для полного справочника `getStoreList` действует отдельный ограниченный лимит ответа 16 MiB; остальные ответы поставщиков сохраняют общий лимит 5 MiB.
- Ошибка или timeout `getStoreList` не должны отменять уже полученные валидные offers. Если название получить не удалось, склад не отображается: внутренний `KEYZAK` пользователю не показывается; authorization и parent abort при этом не подавляются.
- Ошибка основного `ws_search/search` остается supplier integration error. Не превращайте ее в пустой список.

#### PartKOM

- Используется официальный Web Services v4: `GET /v4/search/brands` для connection check и `GET /v4/search/offers` для поиска с Basic Authentication.
- `search/offers` требует `number`; `find_substitutes=0` сохраняет поиск точного артикула без аналогов.
- Официальная документация описывает тело как JSON string, но реальный media type может быть нестандартным. Поэтому bounded body парсится как JSON независимо от `Content-Type`; не возвращайте permissive fallback для невалидного JSON.
- Допускается UTF-8 BOM перед JSON.
- Документация описывает collection напрямую, но реальный API возвращает envelope `{ success: true, data: [...] }`. Boundary обязан проверить boolean `success`, проверить `data` как array и развернуть его одинаково для brands и offers.
- `{ success: false, ... }` является integration error. Не извлекайте и не показывайте raw error values.
- API errors могут приходить как `application/problem+json` с `message`, `detail`, `error` или `title`. IP restriction распознается до общей классификации HTTP status и показывает только безопасное сообщение.
- Серверный public IP должен быть разрешен в настройках PartKOM.
- Runtime credentials могут сохраняться только в общем authenticated encrypted store; whitespace password сохраняется.

#### STParts

- Используются ABCP `user/info` для session check и `search/batch` для поиска.
- Один batch содержит не более 100 brand/article pairs. Не возвращайте старую последовательность отдельных запросов без доказанной необходимости.
- Successful searches кешируются в памяти на одну минуту; cache key должен учитывать реальные search inputs и account context.
- Error envelopes и `errorCode`, включая `301`, остаются integration errors согласно принятому поведению проекта. Валидная пустая result map означает отсутствие предложений.
- `user/info` должен содержать распознаваемое identity field; `{}` не является валидной session.
- Warehouse HTML/color/rating считаются недоверенными и нормализуются до ограниченного набора значений.

#### Forum-Auto

- Используется официальный REST API: `GET /v2/clientinfo` проверяет учётные данные, `GET /v2/listgoods` выполняет точную проценку с `cross=0`, а поиск аналогов — с `cross=1` и выбранным брендом.
- API-пароль передаётся поставщику только по HTTPS и хранится через общий encrypted credential store после успешной проверки. В URL результатов возвращается только публичная страница поставщика: API не предоставляет ссылку на отдельное предложение.
- Ответы ограничены по размеру, должны иметь JSON media type и проверяются структурно. Документированный код 27 («товары не найдены») означает валидный пустой результат; ошибки авторизации и лимитов не маскируются пустым ответом.
- Ошибки REST API распознаются как во вложенном `errors.FaultCode`, так и в плоском формате. В истории код 26 означает отсутствие активных заказов; ошибки доступа, лимитов и оформления сохраняют собственную обработку.

#### MotorDetal

- Token state имеет generation guard; поздняя авторизация не может восстановить token после logout.
- Проверяйте HTTP status, API success/error envelope, обязательные tokens и initialization response.
- Отсутствующая или malformed product page является integration error, а не пустым результатом.
- Auth error очищает supplier session; timeout и integration error не маскируются друг под друга.

#### Механик Ладов

- Browser/context lifecycle всегда закрывается в `finally`; abort не оставляет page/context.
- Shared browser сбрасывается после disconnect и закрывается при application shutdown.
- Storage state записывается только при актуальной generation.
- Пустой или нераспознанный HTML не означает «нет предложений». Успешный empty допустим только при распознанной странице результатов без строк.
- Origin проверяется до navigation, credentials и cookies не попадают в screenshots, HTML dumps и logs.

### Frontend contract

- Frontend остается vanilla JavaScript с native ESM и без bundler/framework.
- Основная таблица показывает только точные предложения и использует тот же comparison-oriented интерфейс, что и аналоги: компактную панель поиска и наценки, счетчик, фиксированные колонки, закрепленную шапку, единую область прокрутки и выделение лучшей цены. Обычный клик по строке не выполняет переход. Контекстное меню основной строки содержит действия «Открыть предложение» и «Показать аналоги», а контекстное меню строки аналога — только переход к предложению; меню также доступно с клавиатуры через Context Menu или Shift+F10. Модальное окно аналогов содержит компактную карточку выбранной позиции, потоковый прогресс, поиск по результатам, сортировку и настройку наценки и сохраняет клавиатурный фокус внутри до закрытия.
- `index.html` загружает `/app.js` через `type="module"`; новые модули импортируются относительными путями и должны обслуживаться static server.
- `app.js` отвечает за DOM state и wiring. Изолированные transport/formatting функции размещаются в `search-stream.js`, `result-formatting.js` и `supplier-search-summary.js`, если не требуют общего mutable UI state.
- Структурированный список применимости удаляет повторы и объединяет пересекающиеся или соседние диапазоны лет только внутри одного OEM-блока исходного артикула. Для объединения должны совпадать марка, модель, тип кузова, код кузова/поколение, объём двигателя, модификация и категория автомобиля (`carType`). Выбранные столбцы не меняют этот ключ; столбец «Модификация» выключен при каждом открытии списка или мультисписка и может быть включён вручную. Основанием для годов служат только исходные применимости этого OEM, без справочного периода выпуска модели. Разрывы между периодами сохраняются. Отсутствующий код кузова объединяется только с таким же отсутствующим кодом, а неполные или некорректные годы допускают только удаление точных повторов. Сохраняются первое появление строки и все OEM-заголовки, а счётчик показывает оставшиеся автомобильные строки. В мультисписке каждый исходный артикул обрабатывается отдельно; сырые данные сохраняют исходные результаты. Это группировка по доступным характеристикам, а не доказательство тождественности разных `carId`: API не предоставляет отдельные коды двигателей или мощность.
- Backend, supplier и `localStorage` data недоверенны. Предпочитайте `textContent`; при `innerHTML` экранируйте каждое значение и отдельно проверяйте URL.
- В `href` и result links допускаются только `http:`/`https:`. Inline event handlers, `eval` и `new Function` запрещены.
- Password/token нельзя сохранять в `localStorage`. Поврежденное persisted UI state должно безопасно сбрасываться.
- Custom SSE parser сейчас сохраняет EventSource-like callbacks и разделитель `\n\n`. Не меняйте parsing semantics без синхронного browser regression-теста.
- Не разделяйте tabs/results/filter blocks механически: они используют общий mutable state. Сначала определите четкий state boundary, иначе callback plumbing увеличит риск regressions.

### Зависимости и runtime

- Целевой runtime: Node.js 26. TypeScript запускается через native type stripping без `--experimental-strip-types`.
- Package manager: `pnpm`; `pnpm-lock.yaml` является обязательным источником воспроизводимой установки.
- Не редактируйте lockfile вручную. После изменения dependency используйте `pnpm`, фиксируйте точную совместимую версию и объясняйте необходимость.
- Сначала проверяйте возможность использовать Node.js standard library. Не добавляйте dependency для простого parsing, timeout, URL validation или atomic filesystem operation.
- После изменения production dependencies обязательно выполняйте `pnpm audit --prod`.
- Не добавляйте фиктивную build-команду: проект не использует bundler и отдельную production build.

## Rossko SOAP Diagnostic

`rossko:search` is a standalone diagnostic utility for the official Rossko SOAP API.
It calls the same official API as the production adapter, but does not normalize results or persist credentials.
It prints the complete SOAP XML response, including all product, stock, and cross fields
returned by Rossko.

The command reuses the authorized Rossko API keys from the application's encrypted
credential store and obtains a compatible delivery method automatically. Run it in
the same service environment, which has access to `STATE_DIR` and
`SUPPLIER_CREDENTIALS_ENCRYPTION_KEY`. It never prints the keys:

```powershell
pnpm rossko:search -- 0532.T5
```

For a one-off diagnostic account, a complete `ROSSKO_KEY1`/`ROSSKO_KEY2` pair may
be provided through the process environment. To inspect the account's checkout
configuration, run:

```powershell
pnpm rossko:search -- --checkout
```

The SOAP API has a 300 requests/minute and 100,000 requests/day limit, and returns
at most 80 product cards and 80 crosses per product.

## Уведомления о заказах на сайте

Круглый колокольчик справа от поисковых вкладок открывает серверную ленту событий:
новые заказы — серые карточки, отмены — красные, получение — зелёные.
Непрочитанные отмены включают красную пульсацию колокольчика. При открытии ленты
сверху показаны только непрочитанные отмены, затем остальные события по времени.
Во время чтения карточки сохраняют место. При следующем открытии прочитанные
отмены возвращаются в общий порядок: новые события идут первыми независимо от вида.
Приоритет действует и при загрузке следующих страниц. Прочтение отмен снимает
пульсацию колокольчика, сохраняя обычный счётчик остальных непрочитанных событий.
При уменьшении движения в системных настройках красная обводка остаётся статичной.
Исчезновение заказа Forum Auto из полного списка активных отмечается жёлтым
предупреждением без предположения о причине. Карточка содержит поставщика,
номер заказа, товары, изменившееся количество, известную стоимость и время
обнаружения по Самаре. Для нескольких товаров есть раскрытие списка.

Один существующий монитор проверяет поставщиков каждые 10 минут с учётом
ночной паузы и занятости поставщиков пользовательскими запросами. Лента работает
без ключа ВК и при выключенной отправке в беседу. Без настроек ВК действует
пауза 23:00–07:00 по Самаре; при наличии настроек используется выбранное расписание.
Первая успешная проверка каждого поставщика устанавливает исходное состояние,
после чего сохраняются новые изменения. Ограниченная выдача поставщика может
скрывать часть событий. Ошибка поставщика не считается отменой или получением.

События и общее для всех компьютеров прочтение сохраняются в той же SQLite-базе,
что и гараж. При открытом колокольчике карточка автоматически становится прочитанной,
когда её номер заказа виден хотя бы наполовину в области списка. Скрытые карточки,
закрытая панель и фоновая вкладка не отмечаются прочитанными. При прокрутке читаются
только попавшие в поле зрения карточки; их порядок сохраняется. Между участками
прочитанных и непрочитанных уведомлений показана заметная разделительная линия.
«Прочитать все» отмечает события только до последнего загруженного номера:
эта команда не захватывает события, пришедшие одновременно с чтением.
Видимые новые карточки затем читаются автоматически по тому же правилу.
Прочитанные карточки остаются в ленте. Прочтение здесь и просмотр отмен в истории
независимы: выбор статуса «Отменено» снимает сигнал истории, а видимость карточки
в ленте — сигнал колокольчика. Эти отметки
не влияют на очередь ВК; для сайта и каждой беседы используются отдельные снимки.

`GET /api/notifications/orders` возвращает `entries`, `unreadCount`, `unreadCancellationCount`, `latestId`
и `nextBefore`/`nextBeforePriority`. Страницы по 30 событий запрашиваются через
`?before=<id>&priority=<0|1>`: приоритет возвращается вместе с курсором и сохраняется
при прочтении карточки, чтобы не пропускать уведомления. Запрос с одним `before`
по-прежнему поддерживается. Курсор продолжает порядок «непрочитанные отмены,
остальные события по времени»; backend и frontend
нужно обновлять вместе. Индекс сортировки создаётся автоматически в существующей
базе без изменения настроек запуска или сохранённых отметок прочтения.
Карточка передаёт до 100 товаров и число остальных в `remainingItems`.
`POST /api/notifications/orders/seen` принимает JSON `{ "throughId": <latestId> }`.
Для автоматического прочтения отдельных видимых карточек используется тот же маршрут
с JSON `{ "ids": [<id>, ...] }`: от 1 до 100 различных существующих номеров.
Два способа прочтения нельзя совмещать в одном запросе.
Браузер читает уже сохранённую ленту каждые 30 секунд при видимой странице;
эти запросы не опрашивают поставщиков и не отправляют сообщений.

## Уведомления о заказах во ВКонтакте

В общих настройках появился раздел «Уведомления ВКонтакте». Единственное
обязательное поле — ключ **сообщества**, которому разрешены сообщения.
Сохранение проверяет ключ и читает список доступных боту бесед. Если беседа одна
в полном списке, она выбирается автоматически; если
несколько или список ограничен, пользователь выбирает её из списка. Проверяется
до 1000 последних диалогов. Этот список не гарантирует обнаружение всех бесед,
в которые пригласили бота. Личные диалоги не выбираются. Бот должен быть
добавлен в беседу и иметь право писать в неё. После выбора беседы бот сразу
отправляет одно тестовое сообщение о подключении агрегатора и будущих уведомлениях
о новых заказах, отменах и получении товаров. В тексте указано, что регулярные
уведомления управляются в настройках; при включении проверка идёт каждые 10 минут.
При нескольких беседах сообщение отправляется только после явного выбора.
Повторное сохранение ключа, обновление страницы и перезапуск сервера не дублируют
успешно отправленное приветствие. После «Отключить ВК» повторное подключение к этой
беседе снова отправит тестовое сообщение.

Если нужная беседа не появилась, используйте **«Подключить беседу по сообщению»**:

1. В управлении сообществом ВК откройте **«Работа с API → Long Poll API»**,
   включите Long Poll, выберите версию **5.199** и сохраните.
2. В **«Типах событий»** включите **входящие сообщения** и сохраните.
3. В агрегаторе нажмите **«Подключить беседу по сообщению»**. Дополнительный
   API-ключ не нужен: используется уже сохранённый ключ сообщества.
4. В нужной беседе выберите бота через `@`, вставьте показанную команду
   `/aggregator …` и отправьте сообщение в течение **5 минут**.
5. Форма автоматически покажет подключённую беседу; бот отправит тест подключения.
   Регулярные уведомления по-прежнему включаются отдельным флажком.

Привязка использует реальный `peer_id` входящего события Bots Long Poll.
Принимается только точная одноразовая команда со случайным 128-битным кодом,
из групповой беседы, от пользователя, для подключённого сообщества. Пересылки,
личные сообщения, исходящие сообщения бота и чужие коды не подключают беседу.
Если ВК вернул пустой список карточек (`messages.getConversationsById`, `items: []`)
или не разрешает читать название беседы (коды 7, 15, 917, 925), показывается её
реальный ID из принятой команды. Пустая карточка не отменяет подтверждённое
входящее событие. Другая беседа в ответе, некорректные данные, ошибки авторизации
или явно указанный выход/исключение бота останавливают привязку.
Возможность отправки проверяется тестовым сообщением: только подтверждённая ВК
отправка отображается как успешная; при отказе видна ошибка тестового сообщения,
а уведомления о заказах остаются выключенными.
Выбранная беседа хранится на сервере и сохраняется при повторном сохранении ключа
того же сообщества, даже если ВК снова не вернул её в списке диалогов.

Прослушивание запускается только по кнопке, заканчивается после привязки,
отмены или через 5 минут. Код и временный ключ Long Poll не сохраняются на диск.
После перезапуска незавершённую привязку нужно начать заново. Отключение ВК,
замена ключа и завершение сервера прерывают ожидание: позднее событие не может
восстановить подключение. Если Long Poll или входящие сообщения выключены,
форма возвращает конкретную инструкцию, а не пустой список.

Чтение административных настроек `groups.getLongPollSettings` может быть
недоступно ключу. Только при отказе с кодом 7 или 15 агрегатор всё равно
запрашивает `groups.getLongPollServer`: привязка начинается лишь после получения
и проверки настоящего сервера событий. Это не подтверждает настройки, которые
ВК не дал прочитать: версию 5.199 и входящие сообщения нужно включить в сообществе
вручную. Прочие ошибки чтения настроек останавливают подключение.
Если доступ к самому серверу событий тоже запрещён, форма показывает метод
и код ошибки ВК и предлагает проверить разрешения ключа **«Сообщения»** и
**«Управление сообществом»**, затем повторно сохранить ключ в агрегаторе.
Отказ Long Poll не означает запрет отправки в беседу: ошибки чтения сведений,
подключения событий и фактической отправки различаются. В сообщения об ошибках
попадают только название вызываемого метода и числовой код, без ответа ВК и ключей.

Для привязки серверу нужен исходящий HTTPS-доступ к `lp.vk.com` в дополнение к
`api.vk.com`; публичный входящий webhook не нужен. Адрес Long Poll проверяется:
разрешён только HTTPS на `lp.vk.com` без нестандартного порта и перенаправлений.
Ключ сообщества не передаётся этому серверу; временный ключ Long Poll передаётся
в query по протоколу ВК, не возвращается браузеру и не логируется. Ответы ограничены
2 MiB, каждый запрос — 30 секундами, обновление истёкшего ключа — двумя попытками.
Форма обновляет состояние раз в 2 секунды только при открытом блоке и активной
привязке; опрос поставщиков при этом не запускается.

HTTP: `POST /api/notifications/vk/pairing` с пустым JSON-объектом запускает
привязку, `DELETE` на том же пути отменяет её. Существующий
`GET /api/notifications/vk` дополнен полем `pairing` с командой, сроком действия
и безопасным сообщением об ошибке либо `null`. Эти маршруты защищаются тем же
доверенным reverse proxy, что и остальные настройки.

Ключ и настройки хранятся с AES-256-GCM в
`STATE_DIR/vk-order-notifications.enc.json` с существующим
`SUPPLIER_CREDENTIALS_ENCRYPTION_KEY`. Без мастер-ключа сохранение отклоняется:
хранение секретов открытым текстом не включается. Ключ не возвращается браузеру,
не сохраняется в localStorage и не передаётся в URL. После сохранения/замены ключа
регулярная отправка всегда выключена; тест подключения отправляется сразу.
Включайте флажок отправки после проверки выбранной
беседы и согласования текстов. Отключение ВК удаляет его настройки и ключ,
сбрасывает отметку теста для выбранной беседы. История и очередь уведомлений
о заказах сохраняются.
Эти настройки защищаются существующей аутентификацией доверенного reverse proxy,
как и настройки поставщиков; отдельная пользовательская авторизация не добавляется.

После включения работает одна серверная проверка каждые **10 минут** независимо
от открытых браузеров и часового пояса сервера. В настройках можно включить или
выключить ночную паузу, изменить её начало и окончание с точностью до минуты и
нажать **«Сохранить расписание»**. Часовой пояс фиксирован: **Самара (UTC+4)**.
По умолчанию пауза действует **с 23:00 до 07:00**; одинаковые начало и окончание
не допускаются. При выключенной паузе автоматические проверки работают круглосуточно.
В начале паузы новые фоновые запросы поставщикам и обычная отправка уведомлений
прекращаются; уже начатый запрос может завершиться в пределах своего таймаута,
его результат сохраняется, а сообщения остаются в очереди до окончания паузы.
После паузы проверка возобновляется автоматически, включая запуск сервера ночью.
Расписание хранится на сервере вместе с зашифрованными настройками ВК и сохраняется
после перезапуска и повторного сохранения ключа. Существующие настройки без
расписания получают прежнюю паузу 23:00–07:00 без повторного подключения беседы.
Ночная пауза не меняет исходную историю: утром сравниваются сохранённые снимки,
поэтому доступные в API ночные изменения обнаруживаются обычным способом.
Проверка не может восстановить заказ, который успел появиться и полностью
исчезнуть из активного API Forum Auto за ночь. Явное подключение/повторное
сохранение ключа и тестовое сообщение доступны в любое время. Время в настройках
уведомлений также отображается по Самаре.

Кнопка **«Проверить сейчас»** вместо «Обновить состояние» сразу опрашивает
подключённых поставщиков и отправляет в выбранную беседу новые обнаруженные
изменения и ожидающие сообщения. Она работает и во время паузы, и при выключенной
автоматической рассылке. При отсутствии изменений сообщения не дублируются;
правило первого снимка без рассылки старых заказов сохраняется. Ручной запуск
не сдвигает следующий автоматический цикл и сроки опроса поставщиков: например,
при циклах 20:00, 20:10 и 20:20 нажатие в 20:06 оставляет следующий цикл в 20:10.
Если автоматический срок наступил во время ручной проверки, параллельный цикл
не запускается, а следующий срок остаётся по расписанию. Если проверка или
пользовательский запрос поставщикам уже выполняется, кнопка сообщает об этом.
Временную ошибку отправки можно повторить кнопкой сразу с тем же `random_id`;
отказ ключа/прав по-прежнему требует исправления подключения.

HTTP: `POST /api/notifications/vk/check` с пустым JSON-объектом запускает ручную
проверку. `PUT /api/notifications/vk/schedule` принимает только
`{ "enabled": true, "from": "23:00", "to": "07:00" }` с допустимыми часами
`ЧЧ:ММ`; `enabled` здесь управляет паузой. Оба маршрута возвращают состояние.
`GET /api/notifications/vk` остаётся чтением состояния без опроса поставщиков и
отправки сообщений; поле `quietHours` содержит сохранённое расписание. Защита
reverse proxy, ограничение тела, проверка JSON и запрет cross-site изменений
применяются и к новым маршрутам. Закрытие ручного HTTP-запроса прерывает проверку.
Новые переменные окружения и зависимости не нужны.

Источник — история API поставщиков, включая заказы,
сделанные на их сайтах. Монитор не вызывает API создания заказов. Первая успешная
проверка каждого поставщика для выбранной беседы запоминает исходную историю без
рассылки старых заказов, отмен и получений. Последующие проверки обнаруживают
новые номера заказов и увеличение подтверждённых отменённых/полученных количеств.
Впервые появившийся архивный заказ с датой раньше дня первоначальной проверки не
объявляется новым; при отсутствии даты возможно сообщить только о первом
обнаружении. Без идентификаторов позиций сравниваются суммарные количества
одинакового бренда/артикула. Пересекающиеся текущая и архивная выборки PartKOM
объединяются консервативно без сложения одинакового товара между выборками.

Отгрузка, готовность к выдаче, возврат и исчезновение из ответа не означают
получение или отмену. Для Armtek, PartKOM и доступных позиций Forum Auto в историю
добавлено необязательное `deliveredQuantity`: фактически полученное количество
при ещё незавершённой позиции. Уведомления содержат именно прирост количества.
Суммы считаются по известной закупочной цене без наценки; неизвестная цена
не заменяется нулём. При объединении одинакового товара с разными ценами сумма
не вычисляется. Настройки не изменяют общие отметки просмотра отмен.
Обнаруженные фоновой проверкой отмены также обновляют существующий журнал отмен.
Просмотр отмен в агрегаторе не отменяет их уведомления ВК: отметка просмотра
меняет только журнал `purchase_order_cancellation`, а монитор ВК использует
собственные снимки и очередь. Это действует и при просмотре до очередного опроса,
и для уже подготовленного сообщения с отложенной повторной отправкой.
Уведомление отправляется при включённой автоматической рассылке вне настроенной
паузы либо при явном нажатии «Проверить сейчас», даже если красная индикация в
агрегаторе уже снята.

Проверки выполняются последовательно, без перекрывающихся циклов. При активных
пользовательских запросах поиска, корзины, истории и подключения поставщиков
очередное фоновое чтение откладывается. Уже начатый запрос завершается с таймаутом;
он не отменяет действия пользователя. Ошибка одного поставщика не отменяет
остальные проверки. В настройках видны время последней успешной проверки,
ошибки каждого поставщика, ограничения выборки и очередь отправки.

Ограничения API: Armtek проверяется за последние 93 календарных дня; PartKOM —
до 500 позиций текущей и до 500 позиций архивной выборки; Rossko — доступная
последняя история с существующими ограничениями нормализации. **Forum Auto
возвращает только активные заказы**: для исчезнувшего заказа отправляется отдельное
уведомление «ТРЕБУЕТ ПРОВЕРКИ» с номером и последними известными товарами.
Причина не присваивается: заказ мог быть получен или отменён, это нужно сверить
у поставщика. Сравниваются только полные успешные ответы; ошибка API или
ограниченная выборка не означает исчезновение. Первый полный ответ после
включения/обновления создаёт исходный список активных заказов без рассылки старых
исчезновений. Повторное отсутствие не дублирует уведомление, в том числе после
перезапуска; если заказ вернулся в активные и снова исчез, это новое событие.
Для остальных поставщиков отсутствие заказа по-прежнему не порождает событий.
Ограниченная выборка может пропустить события; это отображается
в настройках. Переключение учётной записи поставщика требует отдельной сверки
истории: номера заказов в текущей общей модели не разделяются по аккаунтам.

Снимки и исходящие сообщения записываются атомарно в таблицы
`vk_order_monitor_baseline`, `vk_order_monitor_snapshot`,
`vk_order_notification_outbox` существующей `GARAGE_DB_PATH`. Таблица
`vk_order_notification_welcome` связывает тест подключения с сообщением в очереди.
Таблица `vk_forum_active_orders` хранит номера последнего полного списка Forum Auto
для каждой беседы; её обновление и постановка уведомлений выполняются в одной
транзакции с остальными снимками. Новая таблица создаётся автоматически, старые
настройки, снимки и очередь сохраняются; новые переменные окружения не нужны.
Наблюдения Forum Auto используют отдельное пространство ключей `forum-did-v1`:
старые снимки могли содержать меняющийся номер документа вместо ID заказа.
После обновления первая проверка заново запоминает текущие заказы без уведомлений,
а первый полный ответ устанавливает список присутствующих ID. Последующие смены
номера документа или статуса не считаются исчезновением или новым заказом.
Настоящее исчезновение из полного ответа по-прежнему требует ручной проверки.
Переход применяется отдельно для ВК и ленты сайта, не сбрасывает наблюдения других
поставщиков и не удаляет уже записанные уведомления или очередь сообщений.
Временные ошибки теста автоматически повторяются вне настроенной паузы даже при выключенных уведомлениях о заказах;
сообщения о заказах при этом остаются в очереди, поставщики не опрашиваются.
Состояние теста видно в настройках. После исправления ключа/прав сохраните ключ
повторно для повторной попытки с тем же `random_id`.
Одна сводка может
содержать новые заказы, отмены и получение от разных поставщиков; длинные сводки
делятся на сообщения до 3800 символов. Очередь привязана к сообществу и беседе:
смена получателя не перенаправляет старые сообщения. После перезапуска сохраняются
исходная история, очередь и `random_id` для повторных отправок.

За цикл отправляется до 20 сообщений с интервалом не менее 400 мс. Временные
ошибки повторяются последующими циклами с задержкой, максимум 10 попыток;
ошибка ключа/прав приостанавливает отправку. После исправления подключения
повторное включение возвращает неотправленные сообщения в очередь. Недоступность
ВК не блокирует поиск, оформление и сохранение обнаруженных событий.
Проверки прекращаются при завершении процесса, незавершённые HTTP-запросы
прерываются до закрытия базы.

Используется опубликованная схема VK API `5.199`:
[методы сообщений](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json),
[методы сообществ](https://github.com/VKCOM/vk-api-schema/blob/master/groups/methods.json),
[официальный клиент Bots Long Poll](https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/CallbackApi/VKCallbackApiLongPollExecutor.php)
(проверено 17.10.2026). Для исходящих уведомлений публичный webhook не нужен.
Живую проверку с реальными поставщиками и отправку в рабочую беседу выполняют
только после согласования текстов владельцем. Детерминированные проверки:
`node --import ./tests/test-environment.mjs --test tests/vk-notifications.test.mjs`
и `node --test tests/browser/vk-notifications.test.mjs`.

## Production

- Use Node.js 26 and install dependencies from `pnpm-lock.yaml` with `pnpm install --frozen-lockfile`.
- Run `pnpm exec playwright install chromium` when no system Chrome or Edge path is configured.
- Set `STATE_DIR` to a directory outside the application checkout. Restrict it to the dedicated service account because it contains supplier cookies, tokens, and optionally encrypted credentials.
- Set `GARAGE_DB_PATH` to an absolute SQLite path outside both the checkout and `STATE_DIR`. Restrict and back up its directory, including SQLite WAL/SHM files.
- Set `SUPPLIER_CREDENTIALS_ENCRYPTION_KEY` from the deployment secret manager to a base64-encoded random 32-byte key. Do not put the key in the checkout or `STATE_DIR`; losing it requires restoring the original key or moving the unreadable credential file aside and authorizing suppliers again.
- Connect Rossko from the supplier settings using API keys K1 and K2.
- Terminate TLS and require authentication at the reverse proxy before exposing `/api/*`.
- Keep the service bound to loopback and proxy only from a trusted local endpoint.
- Pass supplier credentials and API keys through environment variables or the runtime authorization UI. Do not store them in files in the checkout.
- Armtek stores API-discovered `VKORG` and `KUNNR_RG` in `STATE_DIR/armtek-api-account-state.json`, bound to a hash of the active login and protected with mode `0600`. Explicit `ARMTEK_VKORG` and `ARMTEK_KUNNR_RG` take precedence.
- Armtek uses only its WebService API for authorization and search. API failures are reported as Armtek errors; the service does not query ETP or use a browser-session fallback.
- PartKOM uses only the official Web Services v4 API with Basic authentication. Credentials entered in supplier settings use the common encrypted credential store when its key is configured; there is no browser-session fallback.
- Forum-Auto uses its official REST API with credentials entered in supplier settings. Its password is never included in result links or logs.
- PartKOM Web Services access must allow the server's public IP address. An API `Wrong IP address` response is shown as a safe configuration error without exposing credentials or the upstream payload.
- PartKOM documents successful responses as JSON strings without guaranteeing an HTTP media type. Responses remain size-bounded and must parse as JSON, but a valid JSON body is accepted even when its `Content-Type` is non-standard.
- Current PartKOM responses may wrap the documented collection in `{ success: true, data: [...] }`; the integration validates and unwraps this envelope before normalizing brands or offers.
- STParts uses ABCP `user/info` for session checks and combines up to 100 brand/article pairs in each `search/batch` request. Batch search excludes online stocks by ABCP design; successful searches are cached in memory for one minute to reduce repeated API usage.

Copy the variable names from `.env.example` into the server's secret manager or service environment. The application does not load `.env` files itself.

## Encrypted Supplier Credentials

### PartsAPI proxies

В «Применимости» → настройки → «Соединение PartsAPI» можно добавлять прокси
без ограничения количества, указав публичный IPv4-адрес или доменное имя, порт, тип HTTP или HTTPS
и логин/пароль. В поле «Адрес прокси» вводится только адрес, без протокола,
порта и данных доступа. Домен может содержать до 253 символов и при подключении
должен разрешаться в публичный IPv4. Проверенный результат DNS используется
для этого соединения; локальные адреса и адреса внутренних сетей блокируются.
Для HTTPS-сайтов через обычный HTTP-прокси выберите HTTP: запрос PartsAPI
передаётся в защищённом TLS-туннеле. HTTPS в списке означает TLS-соединение
с самим прокси и требует доверенного сертификата для указанного адреса.
При доменном адресе TLS использует имя прокси, включая SNI; проверка
сертификата остаётся включённой и для прокси, и для PartsAPI.
SOCKS5 не поддерживается; для двухпротокольного прокси используйте его HTTP-порт.
Ручное добавление находится в свёрнутом блоке «Добавить прокси вручную».

Кнопка «Импортировать прокси» загружает текстовый файл UTF-8 размером до 512 КБ,
со строками формата `адрес:порт:логин:пароль`. Число строк и общее количество
сохранённых прокси не ограничены; можно импортировать несколько файлов подряд.
Выберите HTTP или HTTPS для
всего файла; для обычного HTTP CONNECT-порта выбирается HTTP, хотя запросы
к PartsAPI используют HTTPS. Пустые строки пропускаются, двоеточия и пробелы
в пароле сохраняются. Дубликаты по адресу и порту пропускаются без замены
существующих данных доступа. При неверной строке
импорт целиком отклоняется с безопасным сообщением, без вывода данных доступа.
Новые прокси добавляются в очередь без изменения выбранного соединения.

Изначально запросы идут напрямую. Только подтверждённый ответ PartsAPI
`error_code: 5000`, `status: 401` и сообщение
`Exceeded the number of requests from the current IP address.` запускают
автопереключение: прямое соединение → следующий доступный прокси. Запрос
повторяется с тем же API-ключом и артикулом; один маршрут проверяется не более
одного раза за поиск. Обычный отказ ключа, HTTP 429 без этого ответа, ошибка
прокси и timeout не запускают переключение. Общий срок поиска с переключениями
ограничен 30 секундами; срок каждой попытки остаётся 8 секунд. Если доступных
прокси нет, возвращается понятная ошибка, без скрытого возврата к прямому соединению.

Индикатор над результатами показывает выбранное соединение, его число
обращений и автопереключение. При обнаружении смены активного маршрута из-за
лимита IP появляется уведомление с адресом нового прокси; ручной выбор не
требуется. Подробная разбивка доступна при наведении.
В настройках маршруты с подтверждённым лимитом выделены красным. Кнопки
«Выбрать» и «Повторить» меняют маршрут новых запросов, включая повторную
проверку прямого соединения; уже отправленные запросы продолжаются на своём
маршруте. Одновременные ответы не перезаписывают более поздний ручной выбор.
Пометки лимитов снимаются после успешного обращения, при ручной повторной
проверке или после окончания отдельного 24-часового окна соединения.
Первый успешный ответ, включая пустой, запускает таймер только этого маршрута.
Ошибки учитываются в счётчике, но не запускают таймер. При истечении 24 часов
его счётчики и пометка лимита сбрасываются; таймер остаётся нулевым до следующего
успешного ответа. Остальные маршруты продолжают свои окна. Сброс выполняется
перед очередной операцией или обновлением панели; выбранное соединение сохраняется.
В каждой строке отображаются число запросов и обратный отсчёт `чч:мм:сс`;
при наведении на счётчик видны ответы с данными, пустые ответы и ошибки.
Маленькая кнопка `↻` сбрасывает счётчики, таймер и отметку лимита одного соединения.
Это локальный сброс учёта, а не сброс реальной квоты PartsAPI.
Поздние ответы до ручного или автоматического сброса не меняют новое окно.
Счётчик и подсказка индикатора относятся только к выбранному соединению;
при выборе другого маршрута показываются его обращения. Общего таймера нет.
Это локальное окно учёта: PartsAPI не возвращает точное время сброса в
обработанном ответе лимита. Если квота отсчитывается от другого момента,
расчётный таймер может не совпасть со сбросом на стороне PartsAPI.
Считаются все попытки, в том числе отказы, ошибки и отмены. Чтение сохранённых
результатов и добавление прокси не увеличивают счётчики. При перезапуске
сохраняются начало окна, счётчики и подтверждённые отметки лимита; без
мастер-ключа счётчик прямого соединения работает только в памяти процесса.
Сохранённая применимость читается без внешнего запроса и без переключения.
Версия 3 зашифрованного хранилища сохраняет отдельное начало окна каждого маршрута.
При обновлении версии 2 использованные маршруты сохраняют прежние счётчики и
общую границу как своё первоначальное окно; новые маршруты получают отдельные таймеры.

Настройки, выбранный маршрут и счётчики обращений сохраняются в отдельном
`STATE_DIR/partsapi-proxies.enc.json` с AES-256-GCM и существующим
`SUPPLIER_CREDENTIALS_ENCRYPTION_KEY`. Без мастер-ключа сохранение недоступно.
Данные доступа не возвращаются браузеру и не попадают в `localStorage`.
Сохранение прокси не проверяет реальные данные доступа: для проверки выберите
его и запустите поиск OEM-артикула без сохранённой применимости.

Новые маршруты: `GET/POST /api/applicability/proxies`,
`DELETE /api/applicability/proxies/:id`, `PUT /api/applicability/proxy-route`
с `{ "routeId": "<id>" }` либо `{ "routeId": null }` для прямого соединения.
Для сброса используется `POST /api/applicability/proxy-usage/reset` с таким же `routeId`.
В ответах `directUsage` и `proxies[].usage` содержат собственные `windowStartedAt`,
`resetAt` и `secondsUntilReset`; `usage` содержит только сумму счётчиков.
Они используют существующую защиту reverse proxy. Активный прокси можно удалить
после выбора другого маршрута. Обновляйте backend и frontend из одной ревизии;
новые зависимости и переменные окружения не требуются. Существующий файл
API-ключа не мигрирует, поставщики запчастей продолжают работать как раньше.
Для импорта добавлен `POST /api/applicability/proxies/import` с
`{ "protocol": "http" | "https", "text": "..." }`; ответ содержит обычное
состояние маршрутов и `importedCount`/`duplicateCount`. Только этот маршрут
принимает JSON размером до 1 МБ; остальные сохраняют ограничение 16 КБ.

При поиске применимости артикул отправляется только без пробелов и символов,
кроме букв и цифр. Поиск исходного написания больше не выполняется, в том числе
при успешном пустом ответе. Это относится и к ручному поиску, и к импорту OEM;
каждая фактическая попытка учитывается в счётчиках, чтение кэша не учитывается.

Проверки без реальных поставщиков: `pnpm test` и
`node --test tests/browser/applicability-proxy-settings.test.mjs`.
Для браузерной проверки требуется Chromium Playwright либо
`TEST_BROWSER_EXECUTABLE_PATH`.

Supplier session artifacts and supplier credentials are stored separately:

- supplier cookies, browser storage state, and API tokens use supplier-specific files in `STATE_DIR`;
- login/password pairs successfully verified through the runtime authorization UI use the shared `STATE_DIR/supplier-credentials.enc.json` file;
- the credential file contains only an AES-256-GCM envelope with a random IV, ciphertext, and authentication tag;
- `SUPPLIER_CREDENTIALS_ENCRYPTION_KEY` is never written to `STATE_DIR` and must be supplied independently by the deployment secret manager or service environment.

Create `STATE_DIR` outside the application checkout and restrict it to the service account. For example:

```sh
install -d -o <service-user> -g <service-group> -m 0700 /var/lib/autoservice-aggregator
```

Generate one persistent 32-byte master key encoded as Base64:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Store the generated value in the deployment secret manager. The application environment must contain:

```text
NODE_ENV=production
STATE_DIR=/var/lib/autoservice-aggregator
SUPPLIER_CREDENTIALS_ENCRYPTION_KEY=<base64-encoded-32-byte-key>
```

Do not commit the value, put it in `.env.example`, log it, or store it inside `STATE_DIR`. A systemd `EnvironmentFile` containing the key must be owned by root and have mode `0600`. The application does not parse `.env` files by itself.

After the key is configured, authorize each runtime-configured supplier once through the application settings. A successful authorization atomically creates or updates `supplier-credentials.enc.json` with mode `0600`. Password whitespace is preserved. Credentials already supplied directly through the service environment, such as Armtek or STParts API credentials, remain available after restart without being copied from the environment into this file.

On restart, the application loads the encrypted credentials using the same master key. Existing cookies or tokens are reused. A lightweight session validation that receives `SupplierAuthError` performs one bounded full authorization attempt with the stored credentials. Timeout and integration failures do not cause unbounded login retries. Explicit supplier logout invalidates active operations and removes that supplier's persisted session and credential entry.

The same `STATE_DIR` and master key must be retained across deployments and restarts. If the key is missing or does not authenticate an existing credential file, startup fails instead of ignoring the file. Restore the original key whenever possible. If the key is permanently lost, stop the service, move `supplier-credentials.enc.json` to a protected backup location, start the service with a new key, and authorize every supplier again. Do not delete unrelated supplier state files.

Check the encrypted file metadata without printing its contents:

```sh
stat -c '%A %a %U:%G %n' /var/lib/autoservice-aggregator/supplier-credentials.enc.json
```

Expected ownership is the service account and expected mode is `600`. Verify all sessions through the dedicated validation endpoint; this does not run a product search:

```sh
curl -fsS \
  -X POST \
  -H 'Content-Type: application/json' \
  --data '{"article":"90915YZZJ1","suppliers":["rossko","armtek","part-kom","stparts","forum-auto","motordetal","mladov"]}' \
  http://127.0.0.1:3000/api/suppliers/sessions/validate
```

Use the configured local port instead of `3000` when `PORT` is overridden. A result status of `connected` means validation or automatic recovery succeeded, `expired` means manual authorization is required, and `error` means validation was temporarily unavailable.

## Configuration Validation

Configuration is validated when backend modules are loaded. Invalid ports, timeouts, retry counts, supplier URLs, or production state paths stop startup with a configuration error instead of falling back to unsafe values.

- Supplier base URLs must use HTTPS, the documented supplier hostname, and the standard HTTPS port.
- In `NODE_ENV=production`, `STATE_DIR` is required, must be absolute, and must resolve outside the application checkout.
- Browser paths are supplier-specific. A browser path configured for one supplier is not reused by another supplier.
- Password values are not trimmed. Keep intentional leading or trailing whitespace in the secret value.
- Numeric defaults are documented in `.env.example`. Search and navigation timeouts are capped at 120 seconds, retry attempts at five, and retry or polling delays at bounded operation-specific values.

## Public Errors

API responses never include raw supplier payloads, internal URLs, local paths, or exception messages. Authorization request validation returns HTTP 400, rejected supplier credentials return 401, supplier integration failures return 502, supplier timeouts return 504, and unexpected internal failures return 500. Fatal SSE failures use the stable public message `Search failed`; supplier-specific search failures continue to use `supplier_status` events.

## External Request Bounds

Supplier HTTP requests use caller cancellation, bounded request deadlines, approved HTTPS origins, contract-appropriate response validation, and response-size limits. JSON media types are checked when the supplier guarantees them; the documented PartKOM JSON-string exception is parsed from a bounded body. Authorization work is cancelled when the client disconnects and has an overall deadline configured by `SUPPLIER_AUTHORIZATION_TIMEOUT_MS`. Shared HTTP agents and browser resources are closed during service shutdown.

## Session Lifecycle

Persisted supplier state is replaced atomically using restrictive directory and file permissions. Logout invalidates and aborts active work before deleting state, and late operations cannot restore an older session. Authorization is exclusive per supplier: existing searches are cancelled and new searches are rejected until the authorization attempt finishes, preventing old credentials or browser state from overwriting a newly established session.

Session validation uses a dedicated lightweight account/session check for every supplier. It does not execute a product search or emit and discard offers.

Validation runs without a success/progress modal. When a search triggers validation, the search progress panel appears immediately and reports that authorization is being checked while the backend performs one bounded automatic authorization attempt with stored credentials if a supplier session has expired. The UI interrupts the search only when recovery fails or validation is unavailable.

## Empty Results

An empty successful search is returned only when the supplier provides a valid no-offer response. Supplier error flags, API error envelopes, malformed result groups, unrecognized empty HTML, and wholly invalid normalized output are reported as supplier integration errors rather than being converted to an empty result set.
